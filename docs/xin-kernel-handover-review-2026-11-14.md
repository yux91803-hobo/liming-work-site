## 三、安全判断与可复现证据

### 已有的有效边界，应当保留

- 普通任务的 mount/PID/network namespace、清空环境、降 uid/组/能力、禁止再次提权、独立工作副本是真实现；执行器拿不到整个 HOME、控制器库、全部 Cookie 或网关长期 key。
- 推理代理只接受本轮临时 token、固定模型和固定 `/v1/responses` 路径，并有预算；这已经是凭据代理的一种实际应用。
- 出网代理自己解析并检查目标 IP，连接已检查的 IP，能限制私网和 DNS 重绑定到私网的路径。
- 浏览器由控制器持有 CDP 管道。工具没有任意 JS、CDP 或导出 Cookie 的命令；点名站点加载 Cookie、敏感输入暂停、公开浏览器默认无登录，均有行为测试。
- 记忆引用核验、后台笔记不能直接变成个人画像、遗忘抑制和天启不参与默认记忆等保证需要继续回归。

### 本轮复现和处理

| 项目 | 事实与可达性 | 本分支处理 |
|---|---|---|
| 待送达乱序 | 第一条 pending/cooldown 时，`accept` 会直接投递后来的一条；alarm 也会跳过未到期队首。临时存储探针复现同一对话第二句先 delivered。 | 新接收、重发和 alarm 共用队首约束；状态变更串行；闹钟按队首安排；旧尝试回应不能覆盖新尝试。保持原设计的全局 FIFO，不擅自改成跨对话并行队列。 |
| 删除/冲突批准没有绑定范围 | `publishWorkspace(..., true)` 会重新计算并批准当时所有删除。探针先展示删 a，再在等待期间删副本 b，原批准会连 b 一起删。修改副本是必要条件，未证明某个网页能自行触发这个变化。 | 批准绑定任务、真实项目目录、操作清单以及相关文件的前后/当前摘要；网页回传清单 id；范围/内容变了，持久保存新提案并重新展示，旧按钮不能同意新清单。旧无摘要提案先换成新提案，不直接执行。 |
| 高权限路由由模型选择 | 对仅要求总结资料的用户原话，调用 `frontAction` 选择 `--kind system` 会生成 `sandbox:false` 的启动意图，没有独立的宿主授权。探针在事务回滚前截获，**没有启动执行器**。原话虽然逐字保留，却不能限制模型选择权限。 | 这是第二阶段的架构门槛，本轮不声称已封堵。需要真实用户授权来源、受控宿主执行入口和不可由模型扩大的 grant，不能只再加提示词或一句确认。 |
| 电脑维护漏记边界审计 | `boundaryKind` 原来仅覆盖 Harness、Claude、daily，漏了 Codex 的 system 任务。 | 补入实际运行元数据 `routeKind=system`；只留任务/轮次/边界类别，不把可能含 key 的命令正文抄进审计日志。审计仍是检测，不是阻止。 |
| 浏览器日志可保存私人材料 | 原日志写 fill 的前 60 字和网址参数；这与“不导出 Cookie”是不同问题。没有读取线上日志正文来寻找秘密。 | 新日志仅记已知动作、状态、耗时和 origin，不记填表内容、路径/查询串、未知命令正文。原有历史日志不自动删除。 |

另有一个基线测试失败：本轮 Node 22.23.3 下 `npm run check` 为 **739/740**，关闭代理后实际错误为 `EPIPE`，原测试固定要求 `ENOENT`。参照 [nodejs/node #54293](https://github.com/nodejs/node/issues/54293) 的 keep-alive 关闭竞争，改为同时验证“连接失败”和“上游调用次数未增加”，没有删测试，也没有弱化关闭后不能再使用代理的保证。

### 哪些是剩余风险，哪些不能夸大

1. **system、每日任务和天启仍可读控制器 key、改状态与代码。** 普通网页在沙盒中不能直接变成宿主代码，但高权限执行器自己读网页/下载材料后受诱导的路径成立；没有测真实模型被攻陷的成功率。禁用 instabox 插件不能撤掉 shell 和免密 sudo。
2. **私人项目/登录后读到的内容 + 任意公网出站**具备外发路径。限制私网解决 SSRF，不能阻止 POST、查询串或 HTTPS CONNECT 向公网发送私人数据。浏览器的顶层站点限制不覆盖所有子资源；通用 shell 也不经过浏览器按钮风险检测。
3. **浏览器风险词不是完整授权系统。** 中性名称按钮、站点 JS 的实际副作用无法由关键词充分判断。已有“付款/删除/发送”等拦截有价值，但不能因此保证所有外部写操作已经被拦住。
4. 普通沙盒中**尚未发现**可任意导出全部保存 Cookie、读取宿主 key 或绕过私网限制的路径；不将“控制器存在凭据”直接叫作“所有 Agent 都能读凭据”。
5. 同机天启保持 root 级能力时，**不可能同时保证凭据与天启强隔离**。保留它的明确高信任例外，并准确说明信任范围；普通任务不能自动升级成天启。

## 四、怎样借鉴 Meta Muse

核对的是 Meta 的 [How We Built Safety Into Muse](https://muse.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)（2026-09-08），不是 OpenMuse。公开资料说明：Hatch 在隔离运行单元，权限与凭据服务在外侧，Sentinel 管权限和出站，authd 保管凭据并支持替身，浏览器走受控 broker。它的部分实现没有公开源码。

以下是**面向小芯的设计判断**，不是宣称 Muse 的组件可以直接下载复用：

| 阶段 | 采用什么 | 保持的能力 |
|---|---|---|
| 现在 | 修现有批准的范围绑定、顺序与日志问题 | 文件写回、删除、继续任务、浏览、维护都保留 |
| 第二阶段 | 单写者；执行器身份与权限上下文；独立于模型的 host grant；凭据不进入工作状态库或执行器环境；网络策略显式随任务传递 | 用户可授权任务内电脑维护、安装软件、浏览登录网站；同一有效授权内不反复询问 |
| 第三阶段 | 工具/文件/站点操作的细粒度 grant、窄连接器、浏览器与出站统一批准；必要时独立 uid 服务保管凭据 | 为复杂任务提供受控接口；保留用户主动选择的宽授权模式 |
| 暂不采用 | 另租 Secure VM、Postgres、企业策略服务、付费安全模型、eBPF 污点跟踪、全流量 TLS 解密 | 沿用免费 Cloudflare/InstaBox 和 SQLite，控制维护成本 |

浏览器 Cookie 继续由 broker 使用，只给任务“某站点可用”的引用；不要迁入会被对话备份打包的 `workflow.sqlite`。泛用 shell 的 HTTPS 隧道看不到请求体，仅加“域名允许列表”也不能解决向同一允许站点外发。低复杂度方案是把公开研究与私人数据处理分开权限配置；私人数据任务的新目的站点/写操作走程序授权，明确宽授权的范围和剩余风险。

ACP 和 MCP 是协议，不是隔离保证。参考 [ACP 权限请求](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/tool-calls.mdx) 和 [Codex approvals.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/approvals.rs) 的结构化操作身份/参数；先封装现有 app-server 与 Antigravity，按实际安装版本协商能力，不同时替换模型协议、任务调度和前台循环。
