# 天启搬到第二台云电脑 li2 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 首页多一个「天启」工具（`/tianqi`），天启的对话全在第二台云电脑 li2 上跑，和小芯（li）分开；天启的提示词只有「你叫天启。」。

**Architecture:** 一个 Worker 两个「范围」：`/api/xin/*` 是小芯（li），`/api/tq/*` 是天启（li2）。同一套处理，只是换 InstaBox key、换电脑、换待送达实例（`tq-inbox`），模块里的缓存按电脑分开。li2 上跑同一份控制器：Worker 发给 li2 的每个 exec 都带环境变量 `XIN_ROLE=tianqi`，外壳在 `ensure` 时把环境存进 `kernel.env.json`，再传给状态进程和每一轮的进程（`vm-kernel.mjs` 现成的做法）。天启身份下只用 Harness，只认天启用得到的操作。页面是 `site/tools/tianqi/` 里开成「天启模式」的同一个 `chat.js`。

**Tech Stack:** Cloudflare Worker + Durable Object（同一个类 `XinTaskSupervisor`，不迁移）、Node 22 控制器（`node:test`）、Python Playwright 浏览器测试。

**Spec:** `docs/superpowers/specs/2026-11-18-tianqi-li2-design.md`（站长北京时间 11-18 13:39 确认：「不用装stm32编译环境，开始吧」）。

**执行：** Native，Claude Code 在同一会话里实现。站长的长期规矩是由 AI 从写代码到上线全流程完成（CLAUDE.md），站长已说「开始吧」。最后的复核由我自己做（不派子助手），PR 写「实现和自查：Claude Code（同一会话，没有另一位审核）」。

**参考的成熟做法**（写进 PR 和 `docs/CHANGES.md`，实现时先去 GitHub 核对一遍文件路径）：

- 一个服务、几套状态按「范围」分开存：opencode 的 `Instance`（`packages/opencode/src/project/instance.ts`）。它是一个服务进程，状态按项目目录各存一份。这里按范围（xin / tq）分开 key、电脑、Durable Object 实例和缓存。
- 一个环境变量定下整棵进程树的身份：Codex 的 `CODEX_HOME`、Claude Code 的 `CLAUDE_CONFIG_DIR`（本仓库测试里已经在用）。这里用 `XIN_ROLE=tianqi`。
- 进到别的工具时不启动小芯：VS Code 扩展的 `activationEvents`，扩展等到它的视图打开才启动，不在一开始全部启动。

## Global Constraints

- **名字**（spec §4.1、§4.3）：
  - Worker 密钥 `TQ_INSTABOX_API_KEY`，对应的 GitHub Secret 是 `XIN_TQ_INSTABOX_API_KEY`；
  - `wrangler.jsonc` 变量 `XIN_TQ_MACHINE` = `li2`（11-18 核对过，li2 账号里唯一一台就叫 `li2`）；
  - 待送达实例名 `tq-inbox`，环境变量 `XIN_ROLE=tianqi`；
  - 路由 `/tianqi`，页面 `/tools/tianqi/`，接口前缀 `/api/tq/`，浏览器存储前缀 `lm.tq.`（设备号 `lm.xin.device` 两边共用）。
- **文案一字不差**：「你叫天启。」「天启还没配好」「天启没有这个功能」「天启只用 Harness」「天启的网关还没配好」。
- **小芯不变**：`/api/xin/*` 发给 InstaBox 的请求体一个字段都不加（不带 `envs`）。现有单元测试全过；现有浏览器测试只改断言里写着「新建天启」入口的那几处（Task 6 逐条列出）。
- **不迁移**：不做 Durable Object 迁移，不删存储。`tq-inbox` 是同一个类的新实例名；老的 `xin-inbox`、`xin-tasks`、`xin-backups` 不写任何新字段。
- **密钥**：li2 的 key 不进仓库、不进日志、不打印。测试里用假 key，例如 `ibk_tq_key_0987654321`。
- **li 只读**：准备 li2 时只读 li 上的程序文件，不往 li 写任何东西（spec §4.4）。
- **页面截图**：电脑 1280、平板 1024 和 768、手机 390，浅色、深色，自己看过再开 PR。
- **测试**：不跳过、不删测试；改掉的旧断言在 PR 里逐条写明换成了什么。

## Review Focus

1. 同一个 Worker 实例里，小芯和天启的请求交替来：电脑列表、内核配置、`ensure` 节流、脚本核对这几份缓存要按电脑分开，小芯的操作不能发到 li2（Task 1 的「交替请求」「按电脑节流」测试）。
2. `tq-inbox` 的闹钟在一个新的 isolate 里醒来，没有请求告诉它是谁：它要照样用 li2 的 key（Task 2 的「闹钟在新实例里」测试）。
3. 以前在空白页选过天启的手机，本机存着 `lm.xin.agent=harness`：小芯工作台的新对话还要是小芯的主对话，不能在 li 上开出天启对话（Task 6 改的 `xin_main_e2e.py` 第 6 段）。
4. 天启开着时切到别的应用再回来（`visibilitychange`），或者从天启点回首页：首页那一层只在回到首页以后才叫醒 li、打招呼（Task 6 的深链测试）。
5. li2 在睡或在冷却时发消息：消息先存进 `tq-inbox`，页面显示「已收到 · 唤醒中」，电脑醒了再送到（Task 2 的待送达测试和 Task 5 的「唤醒中」浏览器测试）。
