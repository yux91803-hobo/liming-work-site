# 第 2 步第 3 批：恢复加固

状态：3A 兼容版本实现与本地验收已完成；PR/测试站/正式站待验证，默认不分配新编号。基线为 `main@0d1823e`（#152）；#148 已启用常驻状态所有者，#149、#151 已验收冷启动额度超时和空闲暂停。本批只改 VM 内核、兼容桥和相关测试，不改工作台界面。

依据：[已确认设计 §6.6、§7](../specs/2026-11-14-xin-kernel-stage2-design.md)。实际实现由 Codex 负责，自查不算 Claude Code 独立复核。

## 接手判断

- 调度循环、所有权锁、SQLite 单写者、版本化切换和短暂失联的未发送重试已经上线，保留这些实现。
- `processIdentity` 已包含启动时间和 boot id，不再加一套进程身份。
- 现在的 `run_complete` 和任务轮次校验不能区分同一轮的两次执行；兼容桥的具名写入还没有执行尝试身份。
- 收尾尚未暂存。`runner.finish` 在标记 `finished` 后仍会调用可能抛出 `StateUnavailable` 的状态写入；不能把 #148 的短暂重启测试当成长时间失联也不丢结果的证据。
- 第 2 批的定时循环每次都会完整检查，但空闲时隔 60 秒，恢复后到来的请求还不会主动触发一次检查。

## 实施调整：兼容版本先上线，随后启用

直接开始写新协议记录会使自动回滚到 #152 时失去新保证。拆成可独立验证的两段，不修改已确认的总体路线：

1. **3A，执行尝试和恢复检查**：先发布完整的尝试编号读写/校验能力，默认不给无编号的新轮次分配编号；对已有编号始终执行协议。验证并发布这个兼容基线后，再用独立 PR 开启新轮次编号。启用版回滚到兼容版时，进行中的编号仍有效，不能因为默认开关关闭就放过旧报告。
2. **3B，持久收尾和恢复表**：先有尝试隔离，再实现版本化收尾包、持久回执和暂存重放。收尾读取方也必须先成为已验证的回滚基线，再启用写入。3A 不宣称已经解决长时间失联的收尾问题。

### 3A 约束

- 编号由调度者产生，与派发记录一起提交到现有 SQLite journal 的 run 文档；不改表、不回填正在执行的旧轮次。
- 新轮次创建时才选择 `attemptProtocol=1`，旧协议轮次即使恢复时已经开启分配也不升级。已有协议/编号在关闭分配后继续按原协议恢复，避免旧 runner 或旧模块在进行中突然被换协议。
- 编号通过启动环境传给 runner 及其报告客户端。迟到进程只能带启动时的编号，不能临时从新的元数据借用编号。
- 恢复时，活进程继续持有原编号，owner epoch/部署代号变化不改变它；确实死亡、按已有规则重新派发时才换编号。继续保留每轮 `flock` 生命周期锁和现有前台最多重启一次、后台调度规则。
- 派发后另记启动器的 PID/start/boot；PID 上报和启动器记录都缺失时，检查原来的生命周期锁。锁检查出错按“还不能证明死亡”处理。旧子进程没退出前不能换尝试；沿用 TERM、2 秒后 KILL 的身份核对清理。
- 兼容 CLI、内核 RPC、具名写入、单次写入和 `xin` 命令都传递身份。先在控制器入口校验，再执行状态或工具操作；错误不回显编号、正文或凭据。编号是正确性隔离，不是同 UID 进程之间的安全凭证。
- 系统调度、看门狗和空闲整理不能继承上一轮的执行身份。天启沿用自己的轮次和身份，不借用小芯。
- 启动时完整检查；两次检查之间墙上时间跳过 30 秒或倒退时，收到请求即开始完整检查。检查不重叠；空闲仍每 60 秒检查，保持自动暂停条件。
- 把同步状态检查与异步通知投递分开：旧通知还在等待网络时，恢复请求也能重新检查到期状态，但不再起第二个通知循环。SQLite 拿到提交锁后再用库内 run 文档核对编号，不能因 JSON 投影迟到放过旧报告。
- 从空闲转有工作时将定时检查提前到 5 秒；使用单调时钟记录已安排的到期点，只能提前，轮询不能推迟它。异步通知结束时再看一次有无工作，避免沿用通知开始时的空闲判断。

### 3B 实施门槛（尚未实现）

- 收尾包必须一次固定内容：模型结果、用量、会话变化、受控验收结果和停止决定，不能重试时再次累加用量。
- 幂等收尾事务必须覆盖 `run_complete`、后台任务收尾/每日记录/补充输入衔接；重送已提交结果不重做模型、发布或通知。
- 暂存按 run 与 attempt 分开命名，0600、同目录临时文件、文件和目录 fsync；旧 attempt 不能覆盖新 attempt 的文件。
- 恢复先处理有效暂存，再判断是否重新执行。过期/损坏/未知版本保留证据并阻止盲目重跑；不能只按超时认定执行器死亡。
- 验证提交前后 kill、丢回应、重复暂存、owner 停机超过重试窗口、执行器完成后退出、owner/runner 同时死亡、暂停恢复、停止与完成竞争。
- 真实电脑只通过正常 Actions 发布和只读核验；故障注入在隔离的临时状态、模拟执行器中进行。

## 参考和取舍

- [Temporal 的 activity 完成入口](https://github.com/temporalio/temporal/blob/main/service/history/api/respondactivitytaskcompleted/api.go)：收到完成报告后先把 task token 对到当前 activity；小芯借鉴“先核对尝试身份再执行”的顺序，不引入 Temporal 服务。
- [Temporal LocalGate.Update](https://github.com/temporalio/temporal/blob/main/common/timer/local_gate.go)：新的到期点只有更早时才替换活跃定时器。用于从空闲转有活的唤醒，避免连续轮询一直推迟检查。
- [npm/write-file-atomic](https://github.com/npm/write-file-atomic/blob/main/lib/index.js)：临时文件、fsync、rename；[其目录持久化讨论](https://github.com/npm/write-file-atomic/issues/64)说明 rename 后还需同步目录。用于 3B，不新增依赖。
- 没找到可直接复用的小芯旧/新控制器兼容派发实现；保持现有 flock 和 SQLite journal，按本项目的生命周期做最小扩展。

## 回滚和后续边界

3A 的新增字段随 SQLite 的 run 文档保存，无 schema 迁移、无数据删除；旧的无编号在途轮次不补编号。启用后自动回滚目标必须是 3A 兼容版或更新版本；要手动回到更早版本，先排空有编号的执行器并核对结果，不能靠恢复旧备份覆盖新状态。

收尾暂存、宿主授权 C、凭据代理 PoC、工具授权、剩余五处读改写和重活迁出仍按设计分批完成，不借本批改工作台。内核模式尚未连续稳定 7 天，继续保留 legacy 和原有有效测试。


后续凭据 PoC 的平台核对线索（2026-11-16，只读公开资料）：[InstaBox Org Secrets](https://instabox.sh/docs/secrets.md)已有“VM 用占位符，代理向精确 HTTPS 主机注入 header”的能力，先核实当前免费方案是否支持再评估，不能假定必须自建一整套。未指定主机是 `*`，direct Secret 仍让进程拿到明文，都不能当作隔离已完成；这也不替代浏览器 Cookie 托管和逐动作授权。本批不创建工作区/Secrets、不读取或迁移真实凭据。
