### 本次落地

- `finalProtocol: 1` 仅分配给新轮次。`XIN_RUN_FINALIZATION=0` 禁止新分配，现有轮次继续按尝试编号完成。`XIN_RUN_ATTEMPTS=0` 同时停用新编号和新收尾协议。沿用 `commands`、投影和已有启动表，首次有新版执行结果时才创建私有目录。
- 执行器先同步事件记录并保存 `prepared`，受控网页检查、编译完成后保存 `ready`。记录由 64 字节 SHA-256 十六进制摘要、换行和固定 UTF-8 JSON 组成，单个文件上限 1 MiB。目录和文件分别为 0700、0600。排他临时文件同步后，同目录硬链接发布；已有同名文件参与摘要比较。准备或写入中断的证据留给恢复判断。
- `run_finalize` 只接收运行编号和 `ready` 摘要。状态进程从本机文件读内容，以 SQLite 当前尝试及既有回执为准。普通请求和常驻扫描共用恢复判断。完整包同一笔提交运行、用量、统计、任务、通知和交接意图；后台排队的任务状态由常驻调度器继续处理。提交前临时文件或损坏记录会阻止自动重调模型，执行器确认退出后用固定诊断结束本轮，供人工决定是否续做。
- 项目文件阶段以副本和原始清单的摘要开始，备份与预览共用该尝试的稳定发布编号。重新核对原项目，已达目标的文件跳过，删除和冲突按原有审批规则处理，最终提交消费文件回执。临时目录清理有持久待办，由状态进程在提交后处理。用户主动忘记对话时清理该对话的收尾包。
- 失联期间的会话号、线程号和前台用量属于纯报告。终态包保留结算所需的会话变化及用量，应用时维持执行编号检查。一次任意第三方命令的未知执行结果仍需根据现场判断。
- **2026-11-25 尾项补齐记录（Antigravity 实现并自查，无独立 AI 复核）**：补齐上条留下的三项执行器输入与报告协议尾项——（1）`steer_take` / `steer_ack` 两阶段批次认领与确认消费（认领保持 `state: 'pending'` 并挂 `claim: { id, attempt, at }`，模型步完成后再确认 `accepted`；在线确认失败的长失联轮次写入 `prepared.ackedSteers` 由 `finalizeRun` 原子确认，常规轮次不加新字段以兼容回滚 #210）；（2）AGY 原生 `note` / `ask` 按步编号去重重送并保留原回执文本，失联超预算时如实返回 `NOTE_UNCONFIRMED_TEXT` 而不伪造 `已记下。`，同时避免未变化的 `agy_conversation` 重复上报；（3）前台 `openFrontProvider` 的 `front_quota` 与后台对齐容忍传输断线且不重放采样，仍透传 `stale_attempt` / `bad_quota` / 协议错误。**注意**：第 3 批（3A+3B）协议闭环后，第 2 步整体仍未全部完成——第 4a 批（宿主授权方案 C）与第 5 批（`test/xin-writers.json` 的 5 处 `rmw` 清零、`memory-idle` 迁入状态进程定时检查、>50ms 同步重活外移）尚待后续独立批次实施。

Codex 独立审核 #211 后的调整：输入确认扩展保存在独立的 `steer` 文件，并绑定准备包摘要。完整的 `prepared`、`ready` 维持 #210 格式。轮次、模型、步号和执行尝试共同区分原生报告。原批次重送只读自身，换入口成功后才确认交接的插话。详见 CHANGES 和接续 PR 的回归与回滚证据。

Codex App Server 路径同样串行交付插话。回执写入断开时保留模型已经接受的事实，长失联复用 `steer` 文件中的编号列表。连接失败后的实际重试在收尾事件记录原因，新轮次的启动事件记录带入的插话编号。正式联调据此验证保留输入、同一模型和最终结果。

## 1. 需要解决的具体问题

现在 `site/xin/vm-agent.mjs` 的 `runner` 内，`finish` 先设置 `finished=true`，再调用 `saveState`、受控验收、`run_complete`、`task_finish`、每日记录和通知。主人不可用时，状态桥可能抛 `StateUnavailable`，结果还没固定保存就离开了收尾路径。把重试时间从 30 秒改成更大不能解决提交成功但回执丢失、进程同时死亡或进程重启后的重送。

需要保留“这次执行已经产出了什么”，让主人恢复后应用这个固定结果，而不是再次调用模型、再累加用量或因超时重新派发。保证对象是已持久保存的执行结果、逻辑状态与可重放步骤；不承诺任意 shell、网站请求或跨文件系统与 SQLite 的副作用严格 exactly-once。

当前子批的沙盒队列隔离解决另一条入口：工作区复用时，旧 `remember/ask` 请求不能借新 runner 的身份生效。它与本计划共用运行身份思想，但有独立格式、开关和回滚门槛。

## 2. 动手前必须核对的代码路径

| 路径 | 当前行为 | 后续要求 |
|---|---|---|
| `vm-agent.mjs`：`runner`、`saveState`、`finish` | `finished` 早于持久结果；Harness 用量在重入时与库内累计值相加 | 先固定终态输入，重复投递只读同一结果，不能重算累计值 |
| `vm-agent.mjs`：`accept`、app-server `turn` 回调、前台用量回调 | 不只收尾会报告：首次会话号、线程号、用量等也会 `patchSession/patchRun` | 未发送报告暂存或安全保留在本轮状态中；长失联不能使已运行的模型因报告异常提前丢失结果 |
| `vm-agent.mjs`：`iops.run_complete` | 写 done、结束元数据、结束 launch，并衔接补充输入；`statAdd` 是另一条直接文件写 | 运行终态、可恢复后续动作、回执保持一致；不能用两个成功标志掩盖中间空档 |

## 3. 最小接口与状态模型

包的编码、校验、原子保存和读取应有清楚的接口，业务逻辑仍复用现有执行器。#161 后冷启动装控制器已用 40 个子请求，现有测试要求不超过 40，不能再按旧计划默认增加文件。优先在现有报告层（例如 vm-task-reports）承载这些小接口；若确实需要独立模块，先实测并解决上传预算，不暗改阈值，也不为了少一个请求把业务塞回 vm-agent。不要把整个控制器重写成新的框架。

### 3.1 固定终态输入与结果包

- 每次执行使用已有 `run/attempt`，可增加新建轮次才选择的 `finalProtocol`；不升级旧在途 runner。
- 先产生固定终态输入：版本、运行身份、会话号、终止原因、退出码、已观察的模型结果和用量增量、必要的会话变化、受控验收结果或待验收阶段、稳定的创建时间。所有重试使用相同内容，不能重新读取累计用量再相加。
- 字段白名单、嵌套结构、类型和总字节数都校验。上限不得超过状态桥的帧限制；字符串字符数不能代替 UTF-8 字节数。错误不包含正文、Cookie、钥匙或损坏包的片段。
- 摘要使用固定编码，定义清楚摘要覆盖哪些字节。相同身份与内容返回原包；相同身份不同摘要属于冲突，不能以最后到达者覆盖前一包。
- 包不放在任务可写的工作区或其 `io` 目录，不包含整份环境变量、认证资料或任意可执行代码。

若受控验收耗时较长，先持久保存“模型已结束、验收待完成”的原始终态检查点，再执行验收并产生固定结果包。遇到检查点而没有完整结果时，恢复者只能按已定义的阶段恢复或阻止盲目重派，不能当作“没有结果”。不能在 `saveState/patchRun` 已经可能抛错之后才第一次保存这份输入。

### 3.2 文件持久化

- 按 `run/attempt` 分开目录或文件名，旧尝试无法覆盖新尝试。
- 私有目录 0700、文件 0600；目录和目标文件拒绝软链接，打开后核对普通文件与大小，避免跟随任务提供的路径。
- 在同目录用排他方式创建临时文件，完整写入并同步文件，再原子发布并同步目录。原包存在时比较固定摘要，内容冲突时保留原包。
- 已确认包、未完成临时文件和损坏包要能区分。不能把残缺临时文件当作完成结果，也不能静默忽略它后重做模型。
- 收到匹配的持久回执后才可进入已确认状态。清理是后续受控步骤，不能先删包再提交回执。

### 3.3 主人端的完成接口与回执

拟议操作 `run_finalize` 接收版本化结果包，不接收任意状态文件名或任意工具命令：

1. 从当前运行元数据派生目标会话/任务，核对真实调用上下文与 `run/attempt`。在 SQLite 提交锁内再次核对当前尝试，保留 3A 的权威库内检查。
2. 用稳定完成标识和摘要查持久回执。相同结果返回原回执，不重做模型、统计、发布、补充输入或通知；相同标识不同内容报冲突。
3. 在事务中确定停止与完成的胜负，并记录结果所需的会话变化、运行终态、任务阶段、统计、每日记录、交接/通知意图和下一轮启动意图。
4. 提交后返回固定回执。投影修复失败或连接断开不代表事务失败；重试查回执修复投影，不重新进入完成处理。

复用 `commands` 的稳定 ID 和摘要机制，未确认包依赖相应回执持续可读。对现有 `journal.atomic(command)` 验证提交前后的进程退出、提交后的投影恢复和嵌套事务调用。

### 3.4 文件发布不能硬塞进事务

`taskFinish` 现在包含文件验证、项目写回、预览发布、临时目录清理和下一项调度。`publishWorkspace` 已有内容清单、备份与中途补齐能力；预览 `storePreview` 会生成随机 ID；清理会修改真实文件。因此：

- 不能只在外面加一个 `journal.atomic` 就宣称全部副作用原子，也不能把恢复后再次出现的随机预览当作一次逻辑发布。
- 先保存固定发布清单/内容摘要和稳定发布身份，再执行可核对的文件阶段；把阶段结果及回执持久化，最后提交业务完成。内容已经一致的文件可以核对后跳过；遇到原项目变化、未知发布结果或新删除范围，保留原有审批/冲突处理，不自动放宽权限。
- 受控编译与浏览器检查在 runner 的执行域做一次，并把有效性摘要放进结果；重放先验证摘要，不重新跑模型或把旧构建误认作新的可信结果。
- 预览使用稳定的本次发布身份或保存已产生的预览回执，重复应用不得产生多份逻辑预览。
- 通知与交接只在数据库中产生意图，网络发送在事务外由已有 outbox 处理。前台的直接 `pushAll` 收尾也要纳入这一约束。
- 清理放在完成已提交之后，以可重入步骤记录结果；清理失败不能把已完成模型重新派发，也不能为了方便回滚而删除结果证据。

这些步骤可以分成独立小 PR。必须先把相关行为用故障测试固定下来，再决定是否移动现有函数；不要一次搬动所有成熟的项目验收逻辑。

## 4. 恢复、停止与长时间失联

### 恢复顺序

每个恢复入口先修复 journal 投影，再读取本轮收尾阶段/包和回执；检查完毕后才进入原有“进程是否真的死亡”的规则。

| 状态 | 处理 |
|---|---|
| 当前尝试已有完成回执 | 返回原结果、修复投影/后续意图，禁止再派发 |
| 当前尝试有完整有效包、尚无回执 | 应用或继续已记录的完成阶段，不再调用模型 |
| 当前尝试有准备检查点/残缺临时包 | 保留证据，按明确阶段恢复或停在可诊断状态，不盲目重跑 |
| 当前尝试有损坏、未知版本或摘要冲突包 | 拒绝消费并阻止该运行的自动重派，输出固定诊断；不阻塞无关对话和任务 |
| 只有旧尝试的包 | 不得影响当前尝试；保留旧包与已有回执供核对，不能覆盖当前结果 |
| 没有任何完成证据 | 按 3A 的 PID/start/boot、启动器与生命周期锁规则判断，再走原有有限重试 |

不能只在 `reconcileState` 加一次重放：普通请求里的 `runDone`、任务收拾、交接收拾也可能触发恢复或派发，必须共享同一个本轮完成状态判断。

### 停止竞争

- 主人根据事务中的当前状态决定 stopped；包中的旧 `ok=true` 不能推翻用户刚提交的停止。
- 停止先提交：保持已停止决定，保存必要的结果与统计，不发布新项目内容、不消费尚未执行的补充输入。
- 完成先提交：重复停止返回既有完成状态，不制造第二个 done 或重开一轮。
- 补充输入与任务新要求用当前版本核对；旧包可以完成旧执行的记账，不能把新要求覆盖回旧快照。
- 同 UID 的运行编号是正确性凭据，不是宿主授权。保持天启的现有高信任域和默认小芯的既有权限边界，不借收尾重构扩大权限。

### 长失联报告

`accept/saveState`、app-server 线程回调和用量回调也可能向 owner 写状态。必须明确哪些是纯报告、哪些会执行有副作用的命令：

- 未发出的纯报告可以在本轮内暂存，终态包包含最终必要变化；断线不能把“报告失败”误判成“模型工作失败”。
- 已发送但回应丢失的命令不能换新 ID 盲目重试，应依赖同 ID 回执或留下未知状态。
- 一旦尝试被替代，旧 runner 的报告与暂存都要被拒绝；不能为了长失联而跳过 3A 的 fencing。
- AGY 原生 action 的 remember/ask/note 回调与文件队列是不同入口，不能因本次文件桥已有回执就视作这些回调也已持久化。尤其 note 回调遇异常返回空字符串时，运行时会给模型默认「已记下」；后续要用稳定操作 ID 和可确认结果处理未知交付，不能把异常包装成成功。这条静态路径仍须专门故障验收，不在队列启用版改运行代码。

### 运行中插话的消费回执（#161 后新增边界）

临时隔离探针已核对 `steerTake`：先将 pending 改为 accepted 并提交，再把文本返回 AGY。调用方丢弃成功回包后再次 take 为空；AGY 回调在异常时返回空列表，若本轮随后正常完成，`taskFinish` 不把 accepted 带入 inbox。探针使用真实 CLI/tasks 锁/SQLite，未注入真实套接字断线、未调用模型或网络；记录仍在 run 元数据，不能称为物理数据丢失。它证明当前缺少从未知交付恢复逻辑输入的路径，与 note 文件队列开关独立。

- 输入取件也需要稳定批次身份和可重取内容，区分已认领、已交给执行器/模型步骤和已确认；不能在尚无交付证据时把 accepted 当作已消费。
- 同一批次回应丢失后应能取回原批次，不重复消费新输入，也不能简单在每一步重送全部 accepted。
- 运行切换、同轮换执行入口、停止/正常收尾和持久结果包必须共同核对未确认输入；旧尝试不能拿走新尝试的补充。
- 最小验收包括取件提交前/后断线、重复取件、交模型前死亡、正常结束竞态、入口切换及重启，不只验证主动丢弃回包的隔离探针。

先按输入交付阶段独立实现和测试，不直接改一个 catch 或把 unknown 改为 false，也不与 Claude 正在排查的失败补丁混在一起。

本阶段的包持久化不能让任何第三方 shell/网站操作变成普遍 exactly-once。包生成前被杀、外部系统已经执行但没有幂等键等情况仍需检查点与外部状态核对，文档和验收必须准确描述这条边界。

## 5. 发布与回滚

1. 先实现并测试读取、校验、回执和受控恢复能力，默认不给新轮次选择收尾写入协议；已有格式始终读取，开关只影响之后的新轮次。
2. 本地新旧执行协议并存、完整检查和浏览器兼容验收通过后开独立 PR，CI/测试站成功后走正式发布与真实联调，记录准确 SHA 和 Actions 链接。
3. 正式验证这个读取方后，它才成为新的回滚基线；用另一独立 PR 给新轮次启用写入，再重复完整验证与正常只读核验。
4. 回滚不删除新字段/新文件、不恢复旧数据库快照。已有协议轮次和包继续完成。退到不懂收尾的版本之前，必须先排空并核对所有未确认完成状态。

#153/#155 只懂 3A，**不能当作未来收尾格式的安全回滚目标**。队列协议和收尾协议有各自的兼容版本，不因为队列读者上线就误判收尾也可回滚。

部署由 Actions 执行，沿用免费资源、已有数据、权限与凭据。旧状态模式的退役记录见 #169–#171，兼容测试继续覆盖真实状态进程接管、旧执行报告与新版收尾回执。

## 6. 必过验证矩阵

- [ ] 第一次发送前，固定终态包和准备阶段已持久保存；丢回应只会重发相同内容。
- [ ] SQLite 提交前/后分别 kill：没有半提交状态；提交后投影失败可重送修复，done/用量/任务结果不重复。
- [ ] owner 离线超过配置的报告重试窗口，执行器仍能完成并退出；owner 恢复后使用固定结果，没有第二次模型调用。
- [ ] runner 与 owner 同时死亡：完整包、准备检查点、部分临时文件各自走正确恢复路径；未知状态不会自动重做外部副作用。
- [ ] 有完整包时，所有死亡判断入口都先恢复包；活 runner、未登记 PID 与旧子进程的既有保证不退步。
- [ ] 重复包、同身份不同摘要、旧尝试、跨任务目标、未知版本、超限数据、损坏内容与软链接都按限定规则拒绝，不泄漏正文。
- [ ] 停止与完成两种提交顺序、用户补充/任务续做、每日任务、后台等待确认和交接结果保持一致。
- [ ] 受控编译/浏览器检查不因重送重复运行；项目写回中途被杀能按原内容清单补齐或报告冲突，不能扩大删除批准。
- [ ] 重放预览不产生第二份逻辑发布；清理失败不丢结果，outbox/交接的网络发送仍在事务外。
- [ ] 统计与用量提交前后故障不重复、不留下错误成功状态；Harness 与前台累计口径都覆盖。
- [ ] 新旧在途 runner 并存，关闭新分配及回退到已验证的读取方后仍保持已有协议；退到更早版本前排空并核对未确认包。
- [ ] 保留并运行现有学习台、后台任务、浏览器、项目验收、记忆与天启测试，按实际代码调整 fixture，不删行为断言来变绿。
- [ ] 新接口不突破现有冷启动 40 个子请求预算；模块边界和部署请求数一起实测，不放宽已有免费资源约束。
