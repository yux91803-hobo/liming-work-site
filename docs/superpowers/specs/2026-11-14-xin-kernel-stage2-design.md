### 2.2 一处退步（实测）

#137 把待送达改成了「全局只有一个队首」。结果是：一个对话还在跑的时候，如果有一句话发给它（控制器回「上一句还没做完」），发给**别的对话**的话全都排在后面。

探针：对话 A 有一轮跑 40 分钟，先发一句给 A，再发一句给 B。

| | B 那句多久送到 | B 等的时候显示什么 |
|---|---|---|
| main（339c5b0） | 立刻 | — |
| PR #137（3599c2a） | **49 分钟** | 「上一句还没做完，请稍后再试」（这是 A 的原因，不是 B 的） |

根子在于把两种情况当成了一回事：「这个对话在忙」只该挡住这个对话，「电脑叫不醒、在冷却、连不上」才该挡住所有。main 的闹钟那条路也有这个混淆，只是「刚收到就送」那条路把它盖住了。

修法是按对话分道：

- 道的划分：有对话编号的按编号；主对话的第一句单独一道；其余新对话每句各自一道。
- 规则只有一条：**一句话只有排在自己那一道的最前面才能送**。这同时解决了 #137 发现的同对话乱序和这里的跨对话堵塞。
- 电脑整体不可用（叫醒中、冷却、InstaBox 限流）时，这一轮不再试别的道，闹钟定到最早能再试的时候。冷却期间不空转，沿用 #137 的做法。
- 别的等待只挡自己那一道：控制器说这个对话在忙，以及连不上、不明原因的错误。后一种是实施时自查改的：它分不清是电脑坏了还是这一句有毒，当成电脑坏了的话，一句怎么都送不进去的会把所有对话堵到 24 小时放弃为止。各道自己按退避重试，代价只是电脑真坏了时每道各撞一次。
- 排在后面的那句显示「前面那句还没送到」，只在同一个对话里才这样显示。

参考：OpenClaw 的 [命令队列](https://docs.openclaw.ai/concepts/queue) 也是每个会话一次只走一轮，另有一条全局的 `main` 通道限制总并发。

## 3. 目标、不做的、不能出现的

**目标**

1. 内核模式下，`workflow.sqlite` 只有一个进程能写，而且这一点由程序保证，不靠约定。
2. 一次操作不再新起控制器进程。
3. 调度从「每 5 秒转一圈的看门狗进程」搬进常驻进程；执行进程死了、内核死了、电脑暂停又恢复，都不会把同一件事做两遍，也不会丢。
4. 任何时候能切回旧模式，切的过程中消息不丢、在跑的任务不用杀。

**这一步不做**

- 不改模型协议、前台循环、事件格式，不改网页读回复用的 `off` / `pos`。
- 不停写 JSON 投影，不删任何数据（那是第 5 步，要先问站长）。
- 不改天启的功能，不引入框架，不加钱。
- 不新增产品功能。

**不能出现**

- 两个进程同时以为自己是主人。
- 回滚时用旧快照盖掉新消息。
- 为了得到一个「空闲窗口」去杀站长正在跑的任务。
- 为了变绿删测试。
- 新内核变成又一个三千行的大文件。

## 4. 现状和实测

| 项目 | 数字 |
|---|---|
| 现在：只读操作一次（每次起一个 node） | 实测 96–109 毫秒（其中 node 启动 32 毫秒） |
| 现在：会改状态的操作一次（`flock` + 再起一个进程） | 实测 202–216 毫秒 |
| 控制器只加载一次、操作在同一个进程里调用：只读 | 实测中位数 0.1–0.25 毫秒 |
| 同上：一次提交（写一份文档、追加一条事件，落盘并投影） | 实测中位数 1.5 毫秒，最慢 5.9 毫秒 |
| 加载一次控制器 | 实测 74 毫秒，常驻内存 74 MB |
| `lockedCall` 调用点 | 48 处，约 36 个加锁操作 |
| 依赖「每个进程一份」的全局量 | 3 处看 `process.argv[2]==='locked'`，12 处用 `XIN_LOCK` |
| 状态库 | 只有 `workflow.sqlite` 一个（记忆也在里面）；`kernel.sqlite` 只存防重放 |
| 不经过状态库、直接写文件的调用（`vm-agent.mjs`） | `fs.writeFileSync` 22 处、`appendFileSync` 3 处、`logLine` 7 处、`unlinkSync` 24 处 |

控制器有一个好底子：它本来就是「每个请求从磁盘上的状态重新开始」，恢复逻辑（`runDone`、`dispatchLaunches`、`tickTasks`）不依赖进程里的记忆。所以把它加载一次、反复调用，行为是能保持的。要处理的只有三样：进程级的全局量、同步的重活、少数模块级缓存（目前只找到 `vm-memory.mjs` 的两个）。

## 5. 方案对比

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| A | 操作直接放进内核外壳的主线程 | 最简单，只有一个进程 | 控制器大量同步调用（同步 SQLite、同步文件、`spawnSync`），一做重活流和心跳就卡；控制器崩了，监听口一起没；控制器升级必须重启外壳，所有流都断 |
| **B** | **内核外壳照旧，另起一个常驻的「状态进程」执行操作，它是唯一写者** | 外壳一直能回心跳；状态进程可以单独杀掉重启；控制器升级不断流；「谁持有锁谁就是主人」对应一个明确的进程 | 多一个进程，外壳和它之间多一跳（本机套接字，估计 1 毫秒以内，没有实测） |
| C | 重写成全新的异步内核 | 最干净 | 就是总设计 §12 说的「第二版做过头」：三千行的行为要全部重新证明一遍 |

**选 B。** 现有的操作函数原样搬进状态进程，不重写；换掉的只是「怎么串行」和「谁来调度」。

状态进程用子进程，不用工作线程：子进程能被 `SIGKILL` 干净地杀掉，文件锁跟着进程走，SQLite 出了原生层面的问题也不会带走外壳。

## 6. 设计

### 6.1 进程

```
Worker ──HTTPS + 签名──▶ 内核外壳 xin-kernel（常驻；不碰状态库）
                             │ 本机套接字 ~/.xin/run/state.sock
                             ▼
                          状态进程（常驻；唯一写 workflow.sqlite；持有所有权锁；负责调度）
                             ▲ 同一个套接字
      ┌──────────────────────┼─────────────────────┬──────────────────┐
  每轮一个执行进程          一次性进程               xin 命令            清理定时器
  （和现在一样，           （备份打包、登录窗口、    （前台模型用）       （systemd）
    内核重启它不死）         推送、空闲整理）
```

- 外壳就是第 1 步的 `vm-kernel.mjs`：认证、转发、流。它负责拉起和看住状态进程。
- 状态进程是新入口 `node vm-agent-<哈希>.mjs serve`。外壳给它一根管道，管道一断（外壳死了）它做完手上的操作就退出。
- 执行进程保持「每个任务一个」，仍然是脱离父进程的。这层隔离是合理的，要去掉的只是「每个请求一个控制器进程」。
- 新代码分三个小模块，各做一件事：`vm-kernel-owner.mjs`（所有权锁、记录、判断规则）、`vm-kernel-client.mjs`（桥的客户端）、`vm-kernel-state.mjs`（状态进程的循环：收请求、定时检查、看住执行进程）。操作函数留在原处。**`vm-agent.mjs` 在第 2 步里只减不增**，行数写进测试。
- 套接字所在目录权限 0700。容器里的任务够不着它；电脑维护、每日任务、天启和控制器是同一个用户，够得着。这和今天一样（它们今天就能直接改库文件），不是新开的口子，也不当作安全边界。

### 6.2 所有权锁和所有权记录

一个单独的小库 `~/.xin/owner.sqlite`，回滚日志模式（不能用 WAL）。里面一张表，记四样东西：该谁当主人（`legacy` 或 `kernel`）、切换次数（每切一次加一）、桥的协议号、最近一次切换的时间。

锁用 SQLite 自己的文件锁：

- 状态进程启动时以独占方式打开它，并一直不放（`locking_mode=EXCLUSIVE`）。
- 旧模式下，每个要写状态的进程先在这个库上开一个读事务（共享锁），写完才放。一次性的进程（每个请求起的那个、`flock` 里面的那个）从头拿到尾，本来就只活几十毫秒。长时间活着的进程（执行进程、看门狗）不能一直拿着，否则内核永远切不过来：它们只在每一次写的那一下拿。

实测（两个探针，`node:sqlite`）：

| 情况 | 结果 |
|---|---|
| 主人拿着独占锁，旧模式的写者来拿共享锁 | 立刻拿不到（busy） |
| 主人把「归内核管」写进去并提交之后 | 锁还在主人手里，别人仍然 busy |
| 主人被 `kill -9`，它起的孙进程还活着 | 锁立刻释放；别人读到的是已提交的「归内核管、第 N 次」 |
| 旧模式的写者还在写，主人来拿独占锁 | 拿不到，要等它写完 |
| 旧写者结束后 | 主人拿到 |

为什么不用现在到处在用的 `flock`：`flock` 是包在外面的一层进程。包装进程被杀而里面的进程还活着，锁就丢了；不让它丢，锁的句柄又会被状态进程起的执行进程继承走，状态进程死了锁还放不掉。SQLite 的锁跟着进程本身，不会被子进程继承，没有这两个坑，也不多依赖一个外部命令。

**判断规则**。所有写库的入口都先过这一道，而且**每次都重新判断，不缓存**，因为执行进程会活过一次切换：

| 拿共享锁的结果 | 记录里写的 | 做什么 |
|---|---|---|
| busy | — | 主人活着：把请求交给它 |
| 拿到 | `legacy` | 旧模式：和现在一样自己写（`flock` 那套），写完放共享锁 |
| 拿到 | `kernel` | 该内核当主人但它不在：**不写**。等它回来，等不到就回「暂时不可用，可以重试」 |

第三行就是 #137 说的「不能悄悄启动旧调度者」。第一行里如果交不过去（主人正在接手、还没开始听），稍等再按这张表重新判断。

### 6.3 兼容桥

桥有两层，加上一个兜底。

**第一层：操作。** `lockedCall(key, op, args)` 是今天所有跨进程改状态的唯一入口。它的实现换成三种情况：

| 调用发生在 | 怎么执行 |
|---|---|
| 状态进程里 | 直接调用那个操作函数。单线程，天然一个接一个，不需要锁 |
| 内核模式下的其他进程 | 经套接字交给状态进程，同步等结果 |
| 旧模式 | 和现在一样：`flock` + 子进程，期间持有共享的所有权锁 |

调用方的 48 处代码不用改。

**第二层：单次写。** 有些地方不经过 `lockedCall`，直接 `writeJ`（它走 `journal.write`）。内核模式下，非主人进程里的 `journal.write` 和 `journal.append` 自动转给状态进程，作为一次独立的提交。这和今天的语义一样：事务外的单次写本来就是自成一个事务。非主人进程直接开事务（`journal.atomic`）或直接动派发表的，内核模式下一律报错。

**兜底：** 读库一律用只读句柄。非主人进程只有在旧模式、拿着共享锁的那一下才拿得到可写句柄。内核模式下漏掉的写会当场报错，不会变成悄悄的双写。别的进程读库不受影响（比如执行进程组装上下文时查记忆）。

**已经查到的、不经过 `lockedCall` 就写库的地方**（第 1 批处理，写者清单测试防止再长出新的）：

| 哪里 | 现在怎么写 | 改成 |
|---|---|---|
| 每个控制器进程启动时的 `journal.recover` | 谁启动谁投影 | 内核模式下只有主人做 |
| 每个请求进程结束前的 `dispatchLaunches` | 谁处理请求谁派发 | 内核模式下只有主人派发 |
| 执行进程里零散的 `writeJ`（比如 Gemini 不可用的记录） | 直接写 | 第二层桥自动转给主人 |
| Antigravity 执行进程里的 `addMemory` | 记忆模块直接拿库句柄执行写语句（`vm-memory.mjs` 有 7 个修改函数、约 31 条写语句），不经过 `StateJournal` | 包成具名操作，走第一层桥 |
| 空闲整理进程 | 自己开事务，3 处（`vm-memory-idle.mjs` 124、182、192） | 这 3 处各变成一个具名操作，由主人执行；调模型的部分留在它自己的进程里 |

**同步等结果怎么做。** `lockedCall` 是同步函数，调用点很多，不改成异步。做法：每个客户端进程留一个工作线程管套接字，主线程用 `Atomics.wait` 等它通知（[synckit](https://github.com/un-ts/synckit) 是这个路子：工作线程做完用 `Atomics.notify` 通知主线程；主线程那一半我没有读到它的源码，按 Node 的标准用法写）。如果实现时发现有坑，退路是 `spawnSync` 一个三十行的小客户端，一次约 50 毫秒（实测 48，主要是 node 启动），仍然比现在快四倍。

**进程级的全局量。** `process.argv[2]==='locked'` 和 `process.env.XIN_LOCK` 改成每次调用带的上下文。状态进程是单线程，加锁的操作函数都是同步的（事务里不允许等待，`StateJournal.atomic` 已经在检查），所以一个模块级的「当前上下文」变量、进入时设、退出时还原，就够了。

**协议号。** 每次请求带桥的协议号。状态进程接受当前和上一个协议号，这样升级时还在跑的旧执行进程能继续报告。

### 6.4 状态进程里怎么执行

- 入口是今天 `main()` 里「解析完参数之后」的那一段，去掉进程级的东西：结果不写标准输出而是返回；`markCurrentController`、`journal.recover`、`restoreStops` 只在启动时做一次。
- 同步的操作一个接一个执行。带等待的操作（比如 `task_tell` 要先等登录窗口关好）本来就是「先在锁外等，再调 `lockedCall` 改状态」，搬进来以后等待的部分和别的操作交错，改状态的部分仍然是一次同步的提交。
- 重活先不拆。写回时的全项目哈希、备份的 `VACUUM INTO` 这些，先原样在状态进程里做，同时在健康检查里记每个操作的耗时。**上线后看数据，真的超过 50 毫秒的才拆**成「一次性进程做重活，状态进程里一次短提交，提交时核对摘要没变」。#137 给写回批准加的摘要正好能用来核对。
- 外壳给每个操作设硬上限（60 秒）。超了就杀掉状态进程重启：事务回滚，带编号的操作重试时会被去重。
- 状态进程空闲且内存超过阈值（先定 300 MB）时自己退出，外壳立刻拉起新的。
- 模块级缓存逐个查：要么按文件修改时间失效，要么每次操作重读。

### 6.5 不经过状态库、直接写文件的那些

按「出了两个写者会不会坏」分三类：

| 类别 | 例子 | 规则 |
|---|---|---|
| 读了再写 | 预算、额度、计数、通知队列、每日清单 | 必须变成操作，由主人执行 |
| 执行进程自己的输出 | 每一轮的事件文件 `runs/<轮>.jsonl` | 保持一轮一个执行进程在追加；主人只在自己的事务里追加自己的那几行。这是现状，第 2 步不改 |
| 只碰一下的标记、只追加的日志 | 观看标记、`logs/*.jsonl` | 可以留在原进程 |

投影（把库里的内容写成 JSON 文件）只由主人做。非主人进程启动时不再跑 `journal.recover`。

加一个**写者清单测试**：扫一遍控制器源码里所有直接写文件的调用，和一份提交进仓库的清单逐条对。每一条标明属于哪一类。以后谁新加一处直接写，测试就红。

做的时候（`test/xin-writers.json`）类别比上面的表多分了几种：「读了再写」里只发生在操作处理函数里的单列一类（内核模式下操作都由主人执行，已经是单写者），剩下的才是第 5 批要清零的；另外把只由主人写的、内核外壳自己的、状态目录以外的也登记上，免得清单有洞。第一次登记：66 处，其中要清零的 5 处（推送密钥、前台诊断日志、诊断和审计日志、网站登录状态、后台任务的请求预算）。

### 6.6 调度和恢复

实施细化：[2026-11-16 恢复加固计划](../plans/2026-11-16-xin-recovery.md)。先上线尝试协议兼容版本、验证回滚，再启用新轮次；持久收尾按同样顺序后续交付。3A 不代表下面的收尾暂存已经实现。

- 看门狗的循环体（`recover`、`dispatchLaunches`、`tickTasks`、`pumpHandoffs`、发通知、发回调）搬进状态进程：每次提交之后跑一次派发（现在也是这样），另外有一个定时的保险，有活时 5 秒一次，没活时 60 秒一次。内核模式下 `ensureWatchdog` 什么都不做。
- 所有期限按墙上时间判断。两次定时之间隔了超过 30 秒，就当作电脑刚从暂停恢复，马上完整扫一遍。
- 执行进程的启动方式不变（`flock -n` 那一轮的锁，脱离父进程），所以同一轮不可能有两份。
- 每次派发给这一轮记一个随机的**尝试编号**（加字段，旧代码会忽略；同时通过环境变量给执行进程）。进程号、启动时间、开机编号已经有了：`vm-base.mjs` 的 `processIdentity` 记的身份里带 `boot`，`alive()` 会比对（写设计时以为开机编号要新加，做第 1 批时核对代码发现已经在）。
- 执行进程向主人报告时带上轮次和尝试编号。对不上的一律拒绝：旧的尝试改不了新的状态。尝试编号只为了正确，不是安全手段，同一个用户的进程读得到它。

状态进程启动时，以及每次定时检查时，按这张表处理：

| 派发表里的状态 | 执行进程 | 做什么 |
|---|---|---|
| 等待 | — | 按现有的并发、同目录互斥、依赖规则启动 |
| 已派发 | 活着（进程号、启动时间、开机编号都对） | 不动 |
| 已派发 | 不在了，留有收尾暂存 | 应用收尾结果，按轮次去重 |
| 已派发 | 不在了，没有暂存 | 走现有规则：前台那一轮最多重启一次（`dispatchLaunches`，重启时换新的尝试编号）；后台任务由 `tickTasks` 决定接着做还是算失败 |

不会因为「时间到了」就再起一份。判断只看执行进程是不是真的还活着。

**收尾暂存。** 执行进程做完时主人不在（内核在重启）：重试最多 60 秒；还不行就把收尾结果写成 `runs/<轮>.final.json`（先写临时文件再改名）然后退出。主人回来后捡起来。这样「内核死了、执行器活着把活干完」不丢结果。

### 6.7 内核外壳的变化

- `/xin/op`：内核模式下交给状态进程；旧模式下和第 1 步一样起控制器进程。
- `/xin/stream`：外壳自己读事件文件（纯读，`readRunFrom` 抽成公用函数），连上时和之后每 5 秒问一次状态进程（记观看标记、检查执行进程是不是没了、有没有下一轮）。`off` / `pos` 不变。
- 健康检查多报：谁是主人、切换次数、桥的协议号、状态进程的版本和运行时长、各操作的耗时分布。
- 改成写服务文件并 `enable` 的持久服务（总设计 §15 留的第 1 条），`xin-reaper.timer` 就是这么做的。**已只读确认前提**（2026-11-14 北京时间 15:26）：Linger=yes，用户管理器 running，旧内核是 active/transient；尚未真实冷启动验收。持久服务使用独立 `xin-kernel-resident.service`，防止旧 transient 因后台任务残留而遮住新定义，见实施计划。

### 6.8 Worker 的变化

- 新开关 `XIN_STATE_OWNER`（`legacy` 或 `kernel`），和传输开关 `XIN_TRANSPORT` 分开。Worker 每次确认内核时对一下，不一致就让电脑切过去。**期望由 Worker 的配置说了算**，所以 Worker 回滚到上一版，电脑的模式自动跟着回去。
- 退回 exec 时调的是同一个带桥的控制器入口。内核模式下它会把请求交给状态进程，所以 exec 只是换了一条路进同一个主人，绕不过去。
- 新的结果种类「主人暂时不在」：肯定没执行，可以放心重试。待送达按临时错误重试。
- 内核模式下状态进程连续 3 分钟起不来：Worker 自动把期望改回 `legacy`，记一条，用量页显示，推送告诉站长。这个「已自动切回」记在 Durable Object 里，换了部署版本才清掉，所以之后**不会自动再切回内核模式**，等下一次上线或手动改，免得来回跳。只有带桥的入口明确回「主人不在」才算数，端口不通不算（那种情况 exec 还能进到主人）。
- 顺手做掉总设计 §15 留的几条：退回 exec 和退回轮询的次数进用量页；拿不到内核配置时加冷却；送到并确认以后清掉待送达里的消息原文。

### 6.9 切换和回滚

**切到内核模式**（外壳收到 Worker 的要求后做）：

1. 确认没有不懂桥的旧版本控制器进程还活着：看 `/proc` 里的命令行，脚本文件里没有桥协议标记的就算旧版本。有就等，不杀。
2. 让控制器做一次一致的备份（`VACUUM INTO`）。
3. 启动状态进程。它拿独占锁，会自动等正在写的旧模式进程写完（最多 30 秒）。
4. 拿到后写「归内核管」，切换次数加一，然后开始接请求和调度。
5. 旧的看门狗下一圈发现不归自己了，自己退出。还在跑的执行进程不用动：它们下一次报告时按 §6.2 的规则会发现主人活着，交给主人。

**切回旧模式**：状态进程停止接新请求、停止派发新任务 → 做完手上的 → 把投影刷完 → 写「归旧模式」→ 放锁退出。还在跑的执行进程下一次报告时拿得到共享锁、读到 `legacy`，就走回 `flock` 那套。等待中的派发留在表里，旧模式的派发会接着做。

**三种回滚：**

| 情况 | 做什么 | 保证 |
|---|---|---|
| 内核模式有问题，代码没问题 | 改开关，按上面切回旧模式 | 不丢消息，不杀任务 |
| 新版本有问题 | Actions 自动回滚 Worker；上一版的配置是什么模式，电脑就跟到什么模式 | 上一版必须懂桥。所以**第 1 批（桥）上线时保持旧模式**，从第 2 批起每一版都懂桥 |
| 状态进程死了起不来 | 锁已经随进程释放。Worker 3 分钟后经 exec 让带桥的控制器入口把记录改回旧模式（§6.8）。状态进程是卡住而不是死了的话，外壳先按硬上限杀掉它 | 已提交的都在库里；投影由下一个旧模式进程补上 |

不支持直接退回 #136、#137 那样不懂桥的版本。要退，先用懂桥的版本切回旧模式。这一点写进操作手册。

第 2 步新加的状态只有加字段和 `owner.sqlite`、收尾暂存文件，旧模式的同一版代码都认识，所以没有「只有内核懂的状态」需要回译。

### 6.10 宿主授权（§1 ① 选了 B 或 C 才做）

- 授权是一条记录：任务、目标文字的摘要、谁在什么时候批的、有效期。它只能由站长在网页上的操作产生（Worker 验过登录的请求），模型的输出、网页里的文字、后台任务的回答都产生不了。
- 检查放在**派发**的地方：要在电脑本身上跑的任务，启动前程序核对有没有对得上的授权，没有就停在「待处理」。沿用现在 30 分钟没人理就停的规则，以及 #137 做的「批准绑定摘要」。
- 选 C 时，站长发话引出的那一轮由程序自动给一条授权（按那一轮的类别判断，不看模型说了什么）。
- 实施约束：Worker 验过登录才给消息加来源标记，待送达保存标记时保持消息摘要不变。发话派发使用当前对话和当前尝试对应的站长原话。授权核对任务、目录、要求及续做输入，实际启动前再核对期限。未消费的等待审批不占任务槽；每日任务仍以站长的清单为授权。

- 写者清单测试（§6.5）。
- 故障测试，对应 #137 计划里的验收矩阵：提交前后 `kill -9`；内核死执行器活、反过来、都死；`SIGSTOP`/`SIGCONT`；切换到一半杀进程；旧版本进程还活着时要求切换（应该等）；状态进程不在时 exec 进来的请求（应该回「暂时不可用」，不能自己写）。
- 故障测试只在临时目录里做，用假网关和合成数据。正式电脑只做只读核验和正常的上线联调。

## 9. 风险和还没验证的

| 风险 | 对策 |
|---|---|
| 状态进程常驻以后，缓存过期、定时器和句柄越积越多 | 两种模式跑同一套测试；加一个长时间反复调用的测试，看内存、句柄、定时器数量稳不稳；空闲时超阈值自己重启 |
| 状态进程里一个操作卡住，所有操作一起等 | 外壳的硬上限；记每个操作的耗时，超过 50 毫秒的拆出去 |
| 自动切回旧模式被误触发 | 只认带桥入口明确回的「主人不在」，要持续 3 分钟；切回是安全的（锁保证），代价只是变慢 |
| 桥在执行进程里是同步等待，等的时候它自己的事件循环停住 | 和今天一样是同步等（今天是 `spawnSync`，实测一次约 200 毫秒），只是等的时间短得多 |
| 有人把不懂桥的旧版本部署到正在内核模式的电脑上 | 自动回滚只回一版，一定懂桥；手动退得更远之前先切回旧模式，写进操作手册 |

还没验证：

1. 小芯电脑上一次提交要多久。1.5 毫秒是沙盒的数字，电脑的磁盘同步可能慢一些。第 1 批上线后从健康检查里看。
2. 电脑冷启动后用户级服务会不会自己起来（§6.7）。
3. 状态进程经过很多次暂停和恢复后稳不稳。第 1 步的外壳已经在这样跑，状态进程要到第 2 批上线后观察。

## 10. 第 3–6 步因此要调整的地方

| 步 | 调整 |

| 3 统一收件箱和前台循环 | 状态进程里已经有「每个对话一次一轮」和派发表，收件箱事件表加在同一个库里。执行器接口在这一步的开头定（§2.3 第 3 条）。工具闸门的「本次已同意」「先问」两档，直接用 §6.10 的授权记录表示，不另做一套。真正的逐字生成也在这一步；第 1 步只是传输变成了流式 |
| 4 日程、提醒、推送 | 不新建投递通道。日程到点，就是 Durable Object 往现有的待送达里放一行，自己占一道；「存好、叫醒、送到、重试」全部复用 |
| 5 收掉双份状态 | 先做 §2.3 第 2 条挪过来的事：查询改读库。事件文件是留作执行输出还是进库，在第 3 步定。删之前备份，先问站长 |
| 6 安卓平板 | 设备事件是待送达里的一种行；`device.*` 工具一律要授权记录 |

到第 3 步，执行进程不再自己查记忆之后，可以再加一道硬保险：状态进程以独占方式打开 `workflow.sqlite`，别的进程连打开都打不开。现在不做，因为执行进程还要读它。

## 12. 参考

- [tmux `client.c`](https://github.com/tmux/tmux/blob/master/client.c) 的 `client_get_lock` / `client_connect`：客户端连不上服务端时，先在套接字旁边的 `<套接字>.lock` 上拿独占锁，保证只起一个服务端。「客户端经套接字找常驻进程，用一把锁保证只有一个」的做法取自这里；锁换成了 SQLite 的，理由见 §6.2。
- [SQLite 文件锁](https://www.sqlite.org/lockingv3.html)：共享锁、独占锁和进程退出时释放的语义。§6.2 表里的五条是两个探针实测的。「主人在等独占锁的时候，不再放新的写者进来」这一条写设计时只是按文档，做第 1 批时补了探针并写成了测试：4 个写者每 20 毫秒各拿 15 毫秒共享锁，主人 10 轮都在约 20 毫秒内拿到。
- [synckit](https://github.com/un-ts/synckit)：用工作线程把异步的事做成同步调用。
- [OpenClaw 命令队列](https://docs.openclaw.ai/concepts/queue)：每个会话一次一轮，加一条全局通道限制并发。
- #137 计划里已经列的：Codex app-server 和结构化审批、ACP 工具调用、SQLite 备份接口。
- 「同一份代码两种模式并存、所有权可以来回切」这一整套，没有找到能直接套用的现成实现，是按小芯的情况设计的，靠 §8 的故障测试来检验。
