# 平板 AI 主动调用 li、li2：设计

> **已作废（2026-11-26 晚）**：站长实际用过平板后改了方向，平板 AI 改为自己用 InstaBox 命令行直接操控 li、li2，本设计的 `liming-cloud`、`liming-lease` 整体删除。新设计见 [2026-11-26-tablet-cloud-direct-design.md](2026-11-26-tablet-cloud-direct-design.md)。下文保留作记录。

站长于北京时间 11-26 在会话里选定方案「A 云端对话 + 平板后台任务」的完整版。站长看过初稿后认可方向，并要求先核对五个边界：通知会不会丢、请求编号和待发消息怎么恢复、停止中途断线怎么办、冷却和剩余时长分开、用真实 Harness 验证。核对结果写进了 5.2、5.3、5.5、5.6、5.7 和第 11 节。本设计由 Claude Code 写，站长确认后再写实施计划、动代码。上一步见 [平板版 DSH Go 第一步](2026-11-25-tablet-dshgo-design.md)。

## 1. 为什么、要什么

站长 11-26 的原话（节选）：

> 我希望平板上的 AI 是我日常交互的主体。平时聊天、操控平板、读取本机文件，都在平板上完成。当遇到需要编程、研究资料、操作云端浏览器或者长时间执行的任务时，它可以根据实际情况调用 li 或 li2。

> 我希望以后整个 App 只有平板上的 AI 这一个日常交互主体，li 和 li2 都是它可以主动调用的远程执行资源。我不想自己管理主机，也不想为了看任务过程而切换会话或者主机。

> 但是我不想把原来小芯那套复杂的后台调度、内核和状态管理架构重新搬过来。这次我更在乎实际使用体验、响应速度、稳定性和简单程度。

站长关心的几点：两台云电脑能当工具调用；云端干活时平板 AI 照常聊天、操控平板；平板休眠或 App 关掉后云端继续，回来能恢复；聊天界面里能看过程、插话、停止；少唤醒、少长连接、少耗资源；尽量用上游原生能力，以后方便同步 DSH Go。另外要注意断线恢复、重复派发、重复通知、停止是否真停了，以及 InstaBox 自身的休眠和运行时长限制。

## 2. 目标、不做、不能出现的

目标：

1. 平板 AI 能把一件事交给 li 或 li2，立即回到和站长的对话；派给哪台由它按现成信息挑，站长也可以点名。
2. 云端任务的状态、最近几步、插话、停止都在当前聊天页完成：平板横屏时在聊天旁边的侧栏里，竖屏时是弹层，不用切页面、切主机。
3. 做完了平板 AI 主动在聊天里说结果，App 照常弹「一轮完成」通知。
4. 平板睡着、断网、App 被关，云端照常做完；回来后状态对得上，没送到的结果补说一次。
5. 同一次派活重试不会在云电脑上多开一份；同一个结果不重复通知；说「已停止」时云端确实停了。
6. 云电脑只在有活时醒着；做事期间不会因为「看起来闲」被 InstaBox 暂停。

不做：fork 或改 DSH Go 界面（留到第二步）；小芯那样的内核、状态进程、任务队列或调度器；平板引擎被杀期间的系统推送；多块平板之间的协调；改动小芯、天启自己的代码和它们在 li、li2 上用的配置。

不能出现的：日常要切主机才能看任务；平板 AI 等着云端干完才能接着聊；同一件事在云电脑上跑两份；没停说停了；没有任务时还把云电脑一直连着、不让它睡；平板上存能删机器的 InstaBox key。

## 3. 约束（11-26 核对过的事实）

- **Harness（上游）**：
  - 后台任务 `ctx.jobs`：插件可以登记后台任务，登记后立即返回；可以随时更新一行实时进度、追加输出。结束时会给闲着的代理开一轮通知它。停止时插件收到带原因的取消回调。
  - 这套登记只在一个进程里有效：代理被释放时，它名下的任务会被取消。
  - 插件能订阅 `agent/status` 等生命周期事件；能像 `dsh-time-context` 那样，在下一轮开头追加一条带来源的读数。
- **Harness 网页接口（`dsh web`）**：
  - 支持多个客户端同时连。
  - 新建对话可以由客户端指定对话编号（`session/create`）；发消息带请求编号，分「排队」和「插进正在跑的一轮」两种（`session/prompt`）。
  - 停止当前一轮用 `session/cancel`；读历史、实时跟随用 `session/page`、`session/follow`、`session/control`。
  - 列出、停止这段对话起的后台命令用 `job/list`、`job/kill`。
  - 接口和 DSH Go 自己用的 `packages/dsh_client` 一致。
- **DSH Go**：
  - 远程主机的「托管启动」实例在 App 断开后继续运行；实例的进程号、日志（含登录令牌）、启动命令放在远端 `~/.dsh-app-remote/`（`app/lib/remote/ssh/remote_bootstrap.dart`）。
  - 本机引擎上的原生插件可以占这些位置：状态条（`composer.strip`）、面板（`panels`）。面板可放在「对话详情 › 插件」页签，平板横屏时这一列就在聊天旁边；也可以放在聊天页「插件」弹层。插件实时推数据刷新，最快每秒 4 次、每次最多 32 KiB，面板里的按钮和输入框会回传给插件。
  - 工具卡只读，按钮不生效。插件不能发系统通知，也不能切主机。
  - App 自己有「一轮完成」通知（设置 › 通知）。
  - 安卓本机引擎跑在前台服务里并持有唤醒锁，被系统杀掉后尽量重启，但不保证。
- **InstaBox 免费版**：
  - 闲置 30 分钟自动暂停，内存和进程保留，下次使用时恢复。文档明说：只在等模型回复的任务看起来像闲置，可能被中途暂停。
  - 活动租约 `PUT/DELETE /v1/machines/{id}/activity-leases/{taskID}`，单次最长 3600 秒，要续约。租约只防闲置暂停，不延长运行时长。
  - 每轮运行从 120 分钟起，真有使用才往后延，最多 480 分钟；到点强制暂停并冷却。冷却 5 到 20 分钟，接连撞上限依次加长到 60 到 75 分钟、120 到 135 分钟，期间无法唤醒。
  - 只读机器信息（`GET /v1/machines…`、指标）不会唤醒机器；执行命令、读写文件、SSH、拿租约都会唤醒。
  - API key 可以限定权限：`machines:read`；`machines:write`（含执行命令、SSH、租约）；`machines:delete` 单独一项。key 只能管它所在的账号。li 和 li2 在两个账号里。
  - 小芯的 Worker 已经在用租约（`src/xin.js` 的 `xin-tasks`）。
- **li、li2**：分别是小芯和天启的家，CPU、运行时长、网关账号额度都和它们共用。第一步已在两台装好 `dsh-tablet` 包装脚本和 Harness `web` 配置的网关补丁。li 有 STM32 工具链。

## 4. 方案比较

| 方案 | 做法 | 优点 | 不选的原因 |
|---|---|---|---|
| **A 云端对话 + 平板后台任务**（选定） | 任务是 li、li2 常驻 Harness 里的一段普通对话；平板插件把它登记成本机后台任务，并在侧栏里显示、操作 | 云端任务不依赖平板活着；插话、停止、历史都是原生接口；云端对话能接着用，原来的环境自然复用 | — |
| B 远程子代理提供方 | 在 `ctx.subagents` 上注册「跑在 li 上」的提供方 | 有原生子代理界面 | 上游把外部子代理限定为只执行一次、不能插话、只回最终结果；平板引擎一停任务就断，不满足第 3、4 个目标 |
| C 只派活不跟踪 | 一个工具在 li 上开对话就返回 | 最简单 | 不会主动告诉结果，看过程还得切主机 |

A 又分精简版（不加 InstaBox key）和完整版。站长选**完整版**：平板放两把只读 key 看机器状态；li、li2 各放一把不含删除权限的写 key，由云电脑自己续租约，平板睡多久都不影响。

## 5. 设计

### 5.1 总览

```
平板 DSH Go（只连本机）
 └─ 本机 Harness（web 配置）
     ├─ liming-gateway（第一步：平板网关）
     └─ liming-cloud（本设计：模型工具 + 后台任务 + 侧栏 + 台账）
          │  SSH 隧道（按需建立，没任务就断开）            InstaBox 只读 API（不唤醒）
          ▼                                                     ▲
li / li2 上常驻的 Harness（web 配置，DSH Go 托管约定）            │
 ├─ 平板派来的对话：/data/workspace/tablet/<项目>                │
 └─ liming-lease（本设计：有对话在干活就持有租约） ───────────────┘ 写 key（不含删除）
```

一个**云端任务** = 云电脑上的一段对话 + 平板上的一个后台任务 + 平板台账里的一行。平板上的后台任务只是这段对话的「把手」，丢了可以重建；云端对话才是真身。

### 5.2 平板插件 `liming-cloud`

给平板 AI 的工具（越少越好）：

| 工具 | 做什么 |
|---|---|
| `cloud_run(task, machine?, project?, continue_of?, model?)` | 派活或接着做：挑机器（5.3）、确保那台的常驻实例在跑、开对话或在原对话里接着说、登记后台任务，立即返回任务号、机器和挑选理由。`model` 可选，不填就用那台 `web` 配置的默认模型 |
| `cloud_tell(task_id, text)` | 补充要求：这一轮还在跑就插进去；任务已经完成或停止时，等同于 `cloud_run(continue_of=…)`，在原对话里开新一轮、登记新的后台任务 |
| `cloud_machines()` | 两台机器的现状：醒着没有、本轮还能跑多久、冷却到几点、CPU、平板在那台的任务、做过的项目 |

看进度、列任务、停止直接用原生的 `job_output`、`job_list`、`job_kill`；停止由插件按 5.6 执行。插件附带一段简短的使用说明，告诉 AI：长任务、写代码、查资料、用云端浏览器才派；派之前不用问；派完继续和站长聊。

**编号**（防重复的关键）：

- 任务号：平板生成，台账主键。
- 云端对话编号：由任务号确定性生成，用 `session/create` 的 `sessionId` 传给云端。重试时同一编号不会开第二份，云端拒绝重复时按「已存在」接上。
- 请求编号：每条消息一个，补充要求和接着做时都带上。重发不会多出一轮。
- **先写台账，再发云端**：每条要发出去的消息（派活、补充要求、接着做）先以「待确认」写进台账的发件箱，记下请求编号、对话编号、项目目录、原文和插话还是排队；云端回「已接受」后才改成「已确认」。

**中途崩溃怎么恢复**（只依赖两条实测过的上游保证，见第 11 节 E1、E2、E6）：

| 崩在哪 | 重启或重连后 |
|---|---|
| 写了台账，云端对话还没建 | 用同一个对话编号、同一个目录再建一次，再发同一个请求编号 |
| 云端对话建好了，消息没发出去 | 再建一次（同编号同目录返回的是原来那段），再发同一个请求编号 |
| 消息已被接受，回执丢了 | 再发同一个请求编号：云端从自己的日志认出来，只回「已接受」，不多一轮 |
| 云端收下消息、还没写进日志就崩了 | 再发同一个请求编号：日志里没有，按新消息收下，不会漏 |

发件箱里的「待确认」在下一次连上那台机器时依次补发，补发成功前，面板显示「正在送达」。

**台账**：`~/.liming-cloud/tasks.json`（权限 600，先写临时文件再改名，带版本号）。每行记：任务号、所属平板对话、机器、云端对话编号、项目目录、标题、状态、开始和结束时间、最近同步位置、发件箱、停止请求、通知状态、结果摘要。只存这些，不存云端对话内容。

**状态**：派发中 → 进行中 → 完成、失败、云端中断或已停止；停止中是停止请求已记下、还没确认的过渡状态。另有三个只用于显示、不改台账的情况：连不上、等待机器醒来、冷却到 HH:MM。

### 5.3 选机器：四条规则，不写调度器

`cloud_run` 没点名时，插件用只读 key 看两台机器（不唤醒），按顺序筛：

1. **正在冷却的排除**：冷却期间怎么都叫不醒，面板显示「冷却到 HH:MM」。两台都在冷却时，不派，告诉 AI 最早几点能用，由它和站长商量。
2. **本轮剩余运行时间不足的靠后**：剩余不到 45 分钟的排到后面，有别的选择就用别的；只剩它能用时照样派，并告诉 AI「这台大约 N 分钟后会暂停，到时任务冻结，冷却结束后接着跑」。
3. 接着某个已有项目做（`continue_of`，或台账里有同名项目），回原来那台；明显要用 STM32 工具链的去 li。
4. 醒着的优先：省约 40 秒唤醒，也不新开一轮计时。
5. 闲的优先：先比平板在那台跑着的任务数，再比 CPU；还分不出就选最久没用的那台。

每台同时跑的平板任务数有个上限，**初始为 2**，是插件设置里的一项（App 原生的插件配置表单），站长可以随时改；超了先用另一台，两台都满时告诉 AI 现状。挑选理由写进工具返回，AI 可以照搬给站长。

某台的只读 key 没装或读失败时，这台退回精简版的判断：只看台账里最近一次联系的时间和平板在那台的任务。规则 1 和 CPU 比较对它不生效，面板上标「状态未知」。

### 5.4 界面：都在当前聊天页

- **派活回执**：`cloud_run` 的返回带工具卡，聊天记录里显示「已交给 li2 · 研究 XX · 任务 3」。工具卡只读、不刷新，只当回执。
- **状态条**：输入框上方一行，例如「☁ li2 研究中 · 7 分钟」，有完成未读时显示「☁ 1 件完成」。点它打开面板。
- **「云端任务」面板**：
  - 放在「对话详情 › 插件」页签：平板横屏时就是聊天旁边的侧栏，你说的副屏；也放在聊天页「插件」弹层，竖屏或手机用。
  - 每个任务一张卡片，写着：标题、机器、状态、已用时间、机器本轮剩余时间、最近 3 步（展开看本次的步骤时间线）、完成后的结果摘要。
  - 卡片上的操作：「插话」（输入框 + 发送）、「停止」（要确认）、停止或完成后的「接着做」。
  - 内容实时推送，最快每秒 4 次，每次不超过 32 KiB。步骤只推标题和短摘要，展开时再取。
- **步骤怎么写**：从云端事件里取三类——调用了什么工具（名字 + 一句话参数）、AI 说了什么（截短）、这一轮的结束原因。不搬运完整输出。
- 原生「全部功能 › 后台任务」照样能看到这些任务的实时输出，作为备用入口。
- 让聊天记录里的卡片本身能展开、能操作，以及藏掉切主机入口，留到第二步 fork。

### 5.5 通知：不丢，也不重复

以平板这段对话自己的日志为准，「已告诉」只在确认通知进了日志之后才记：

1. 云端这一轮结束，台账先记「完成，通知未确认」。
2. 插件结束对应的后台任务。Harness 把完成通知作为一条用户消息记进平板对话的日志，来源标记是 `{kind: 'tool-jobs', form: 'notice'}`，正文带后台任务编号。代理闲着就给它开一轮，它在聊天里告诉站长，App 弹「一轮完成」（见第 11 节 E7a、E7f）。
3. 插件在进程内看到这条通知写进了日志（`session/event`），才把台账改成「已告诉」。

引擎在第 1、2 步之间被杀，或者原来的后台任务已经不在了：

- 插件重启后，先按任务编号、后台任务编号去那段平板对话的日志里找通知，找到就补记「已告诉」，不再发。
- 找不到，就等那段对话的代理出现（站长打开或使用这段对话、引擎把它加载起来时；用 `agent/created` 接住）。代理一出现就补投一条通知：做法照 `tool-jobs`，代理闲着用 `followup` 开一轮，忙着用 `inject` 插到下一步。来源标记写 `{kind: 'liming-cloud', form: 'notice', taskId}`，写进日志后才记「已告诉」。
- 在补投之前，面板和状态条一直显示「完成（未读）」。

所以完成通知不会永久丢；唯一可能重复的情况，是日志里的通知没认出来。补投和原通知都带任务编号，认的依据固定，测试里覆盖。

上游的限制：没有被加载的对话，插件没法在它里面开一轮（代理表只能 `get`，`tool-jobs` 在这种情况下也是直接丢掉）。所以平板引擎重启以后，主动提醒要等你回到那段对话；在那之前，状态条和面板会先告诉你。

### 5.6 停止：说停了就是真停了

停止有四个来源：AI 用 `job_kill`、站长在面板上点「停止」、站长在 App 的「后台任务」页点停止、站长归档这段平板对话。

**先记下，再执行**：台账先记「停止中」，带来源、原因和时间，再动手。下面几步都可以重复执行，中途断线或引擎被杀，重连或重启后就接着做，做完为止：

1. 停掉云端这一轮（`session/cancel`）。空闲时重复调用也只回「已接受」（E4）。
2. 停掉这段云端对话起的后台命令（`job/list` 列出，`job/kill` 逐个停）。停掉这一轮不会连带停掉它们（E5）；对已经结束的命令再停一次，回「已经结束」。
3. 清掉这个任务项目目录下残留的进程。云端 Harness 崩溃重启后，原来的前台命令会变成孤儿继续跑，而且后台命令表只在内存里，重启后就忘了（E6）。所以复核时按「工作目录在这个任务的项目目录下」找进程，先 SIGTERM，不退再 SIGKILL，并记下停了哪些。
4. 复核：这一轮已结束，后台命令和残留进程一个不剩，才把任务标成「已停止」。

做到一半连不上时，面板显示「停止中（正在确认）」，确认后才报「已停止」。项目目录以外、云端 AI 自己脱离管理另起的进程，按实际情况写明，不说已停。

**取消原因要分清**：平板这边的后台任务被取消，不一定是要停云端。下表的原因字符串是实测值，0.2.2-rc.1（平板）和 0.2.2-rc.3（li、li2）一致（E7b 到 E7e）：

| 取消原因 | 来源 | 云端怎么办 |
|---|---|---|
| 模型填的任意原因 | AI 调 `job_kill` | 按上面几步停 |
| `cancelled by the user` | App「后台任务」页或网页停止 | 停 |
| `session archived` | 归档平板对话 | 停（和 Harness 归档时停掉后台工作的语义一致，我的取舍） |
| `owner disposed`、`jobs service disposed`、`jobs teardown`、`teardown` | 平板引擎关闭、插件重载、代理释放 | 不停，只解除关联，台账保持「进行中」，下次对账接上 |

面板上的「停止」不经过取消原因，直接走上面几步。单测里扫描当前安装的 Harness 源码，核对「释放类」原因的清单；以后升级 Harness 时如果多了新的释放原因，测试会先失败，不会误停云端。

### 5.7 断线与恢复

- SSH 隧道每台机器一条（复用连接），只在三种情况下建立：派活或接着做、有任务在进行且平板醒着、站长打开面板或 AI 查进度。没有进行中的任务时断开，让云电脑按时休眠。
- 掉线后有任务就按退避重连；重连后从云端对话的历史补齐，再接着实时跟随。补齐依据台账里的最近同步位置。
- 插件启动时读台账：「进行中」的任务先只读查机器状态；机器醒着才连上对账，睡着的等站长打开面板或开口时再说（任务若还在跑，机器会因租约保持醒着；睡着通常说明已经做完或被冷却）。
- 对账后的处理：仍在跑的重新登记后台任务，并接上实时跟随；做完的按 5.5 补说；发件箱里「待确认」的按 5.2 补发；「停止中」的按 5.6 接着停；云端对话找不到的标「失败：云端对话不见了」，不重派。
- **云端中断**：云端 Harness 崩溃重启后，原来那一轮既不在跑，日志里也没有结束记录（E6）。对账时，如果对话不在跑、最后一轮又没有结束记录，就标「云端中断」，面板提供「接着做」（新的请求编号，在原对话里说「接着做」），同时按 5.6 第 3 步清理残留进程。不自动重派，由 AI 和站长决定。
- 判断「在跑」和「同步到哪」：用对话列表里每段对话自带的 `running` 和 `asOfSeq`，读历史用 `session/page`，不另造状态。

### 5.8 InstaBox：租约、时长和冷却

- **云端插件 `liming-lease`**：
  - 装在 li、li2 的 Harness `web` 配置里，跟着常驻实例启停。
  - 只要有代理在忙（`agent/status`），或有后台命令在跑，就持有租约 `tablet-cloud`：TTL 3600 秒，每 20 分钟续一次。全部空闲 2 分钟后释放。
  - 用哪台机器由装机时写入的机器名（`li` 或 `li2`）决定，插件用写 key 列出本账号的机器，再按名字找到编号。找不到或不止一台同名时不拿租约，只记日志。
  - key 读不到或调用失败时只记日志，不影响任务本身，只是可能被闲置暂停。
- **只读看状态**：平板用只读 key 读两台机器的状态、本轮开始时间、上限、冷却截止时间和 CPU 指标，用于 5.3 和面板显示，从不唤醒机器。
- **时长**：租约不延长免费版的运行时长；真在干活的任务一般有 CPU 和命令使用，会被延长，但单轮最多 480 分钟。面板显示本轮剩余时间；剩余不到 30 分钟时，状态条和面板提醒，AI 会被告知，可以让云端先收尾、记下进度。
- **冷却**：机器在冷却时显示「冷却到 HH:MM」，不派新活。冷却期间进程是冻结的，冷却结束后任务被唤醒就接着跑。插件不反复去叫，只在冷却截止时间之后、且有进行中的任务时连一次。
- 免费版接连撞上限冷却会越来越长，还会连累小芯和天启，所以插件不为平板任务额外保持机器醒着：有任务就有租约，没任务就放。

### 5.9 云端常驻实例

- 每台机器只跑一个 `web` 实例，平板插件和 DSH Go 的调试连接共用它。两个实例同时写一份会话存储，上游明说没有协调。
- 插件照 DSH Go 托管启动的约定（`~/.dsh-app-remote/` 下的进程号、日志、启动命令）去复用或启动实例，启动命令就是第一步装好的 `dsh-tablet`。这部分约定单独放在一个模块里，测试里对照 DSH Go 源码的写法；DSH Go 升级改了约定时，只需改这一处。
- 发现活着但启动命令不同的实例时，照 DSH Go 自己的做法：不杀、不重启，派活失败并说明原因，由站长决定。只有确认进程已经死了才自己重新拉起。
- 平板派来的对话都在 `/data/workspace/tablet/<项目>` 下，不碰小芯、天启的目录和它们的 `headless` 配置。

### 5.10 密钥与安全

| 放在哪 | 什么 | 权限 | 用途 |
|---|---|---|---|
| 平板 `~/.liming-cloud/secrets.json`（600，在 App 私有存储里） | li、li2 的 SSH 令牌 | 能登录那台机器 | 建隧道 |
| 同上 | li 账号、li2 账号各一把 key | 只有 `machines:read` | 看状态，不唤醒 |
| li、li2 的 `~/.liming-cloud/lease.key`（600） | 各自账号的 key | 只有 `machines:write`，不含删除 | 云端自己续租约 |

- 和第一步不同：SSH 令牌这次要长期存在平板上，否则 AI 没法自动派活。
- 装机脚本用终端读入这些值，不回显、不打印、不写进仓库；任何一把都能随时在 InstaBox 后台吊销，平板丢了先吊销这四样。
- 不在平板上放带写权限或删除权限的 InstaBox key。

### 5.11 装机变化

装机脚本 `site/tablet/setup.sh` 增加：读入并保存两台的 SSH 令牌（可跳过某一台）；读入四把受限 key；装 `liming-cloud` 到平板、`liming-lease` 到 li 和 li2；把写 key 放到对应机器上。可以重复跑，已装的跳过。

站长要做的事：在 li、li2 各自的 InstaBox 账号里各建两把 key（一把只读、一把只写不删）；然后在平板上重跑一次装机命令，按提示粘贴。`docs/tablet.md` 同步改：日常不用切主机，「远程主机」只留作调试。

## 6. 参考的成熟做法

- **Claude Code**：后台任务和完成通知。主对话不被占，做完把结果作为一条通知交给主代理；随时能看输出、停止。本设计里的平板后台任务就是这个形状。
- **OpenAI Codex 云任务**：把活派到云端环境，本地接着做别的，回来看结果、接着在同一个任务里说。
- **Google A2A 协议**：远端代理的任务有明确状态（进行中、需要输入、完成、失败、取消），断线后可以重新订阅续上。本设计的状态和「补齐再跟随」照这个思路。
- **opencode**：一个服务端，多个客户端同时接同一段对话。对应这里平板插件和 DSH Go 调试连接共用一个云端实例。
- **InstaBox 活动租约**：官方给「等模型的长任务」的解法；本仓库小芯的 Worker 已在用（`src/xin.js`）。
- 上游的 `dsh-time-context`（追加读数）、`dsh-tool-jobs`（完成唤醒）、DSH Go `dsh_client`（`dsh web` 接口的参考实现）。

## 7. 验收

自动化（`npm run check`，`node --test` 单测，全部离线，用假的 `dsh web` 服务和假的 InstaBox API）：

- 派活重试、崩溃在「派发中」之后，云端只有一份对话；补充要求重发只多一轮。
- 完成通知只发一次；引擎重启后「完成未告诉」在下一轮补说一次。
- 三步停止：云端那轮还没结束、或后台命令还在时，不报「已停止」；取消原因表里每一行各有一条测试。
- 选机器四条规则，每条一条测试；冷却、剩余不足、两台都满的情况。
- 断线重连从同步位置补齐，不重复、不丢步骤。
- `liming-lease`：忙时持有、每 20 分钟续、空闲 2 分钟后释放、key 失败不影响任务。
- 面板和状态条推送的数据不超过 32 KiB、不超过每秒 4 次。
- 密钥文件权限 600；任何输出、日志里不出现令牌和 key。

真实 Harness 契约检查（每次发布、每次升级 DSH Go 或云端 Harness 前都跑）：

- 用和平板（DSH Go 锁定的版本）、li/li2 一样版本的真实 `dsh web`，加一个本地模拟模型服务，把第 11 节的实验做成可重复的脚本放进仓库：重复建对话、重复请求编号（含崩溃重启后）、插话进同一轮、停止前台工具、停止后台命令、崩溃后的孤儿进程、完成通知只唤醒一次并写进日志、四类取消原因。
- 再加两项：插件在进程内确认通知写进日志后才记「已告诉」；引擎重启后在对话的代理出现时补投一次，日志里只有一条。
- 这些脚本要装真实 Harness（约 0.6 到 1.3 GB），不进每次 PR 的 CI，在本机或单独的工作流里跑，结果写进 PR。

真机（站长装好后对照）：

1. 让平板 AI 研究一个 GitHub 项目：它派给某台并说明理由，立刻能接着聊、操控平板；侧栏实时显示步骤。
2. 中途在面板插话，云端这一轮照办；再点停止，面板先显示「正在确认」，再显示「已停止」，云电脑上确实没有残留。
3. 派一个长任务后锁屏 40 分钟：云电脑没被闲置暂停（租约），回来后结果已在聊天里，或者打开 App 后补说一次。
4. 没有任务时 30 分钟后两台都自己休眠。
5. 小芯 9:10 的每日任务、天启照常。

## 8. 留给实现者决定的

- `dsh web` 接口的 JS 客户端：照 `dsh_client` 写一个最小的（登录换 cookie、`POST /api/<端点>`、`/api/remote.mux` 跟随），或复用上游现成的客户端包。前提是不给平板插件引入要编译的依赖。
- SSH 隧道用系统的 `ssh`（第一步装机已装 openssh-client）加 ControlMaster，还是用 Node 实现，选更稳、依赖更少的。
- 事件到「步骤」的具体映射和截短长度；面板组件的具体排布（遵守 DSH Go 插件设计规则）。
- 云端两台 Harness 的版本核对和锁定办法；不一致时插件怎么报错。
- 台账和 secrets 的文件格式细节、迁移办法。
- 项目目录名怎么从任务标题生成（只用 ASCII，带短编号）。

## 9. 风险

- **上游接口变动**：Harness 的后台任务、事件和 DSH Go 插件协议都还在 0.x、预览版阶段。版本要锁定，升级时重跑本设计的验收。
- **依赖 DSH Go 内部约定**：`~/.dsh-app-remote` 不是公开接口；已隔离在一个模块里，并用测试对照。
- **资源共用**：平板任务会占小芯、天启的 CPU、运行时长和网关额度。用 5.3 的上限、5.8 的及时放租约来减小影响，但不能消除。
- **平板引擎被杀**：被杀的那段时间没有通知，回来补说；DSH Go 文档自己也说不保证熄屏存活。
- **密钥变多**：四把 key 加两个令牌，靠最小权限和吊销兜底。

## 11. 已用真实 Harness 核实的行为（11-26）

站长要求在实施前用真实 Harness 核对关键接口，不等到平板上才发现和设计不一致。做法：在会话容器里起真实的 `dsh web`（`--profile web`，Node 24.22.3），模型线路指向一个按 OpenAI Responses 流式格式回复的本地模拟服务，用 `dsh web` 的公开接口（`POST /api/<端点>`）操作；另装一个探针插件，登记可控时长的后台任务并记下取消原因和代理事件。版本：0.2.2-rc.3（和 li 上一致）跑全部实验；0.2.2-rc.1（照 DSH Go `runtime/locks/dsh-0.2.2-rc.1` 原样安装，和平板一致）重跑了 E7 全组。脚本和日志在会话临时目录，实施时整理进仓库（见第 7 节）。

| 编号 | 做了什么 | 结果 | 对设计的影响 |
|---|---|---|---|
| E1 | 同一编号同一目录建两次对话；再换目录建一次 | 第二次返回原来那段；换目录报 `session/conflict` | 用确定性编号建对话可以放心重试（5.2） |
| E2 | 同一请求编号连发两次，空闲后再发一次 | 只有 1 条消息、1 轮 | 回执丢了就用原编号重发（5.2） |
| E3 | bash 前台命令跑着时发「插话」 | 下一步就进了同一轮，没有另起一轮 | 「补充要求」直接用原生插话（5.2） |
| E4 | 前台命令跑着时停止；空闲时再停一次 | 命令进程被杀，这一轮以 `aborted`、原因 `user` 结束；再停回「已接受」 | 停止可以重复执行（5.6） |
| E5 | 后台命令跑着时停止这段对话 | 后台命令**还在跑**；`job/kill` 才停，再停回「已经结束」 | 停止必须分步并复核（5.6） |
| E6 | 前台命令跑着时强杀云端 Harness，再重启 | 命令成了**孤儿继续跑**；对话还在，但那一轮既不在跑也没有结束记录；后台命令表清空；同一请求编号重发仍只算一次 | 新增「云端中断」状态和残留进程清理（5.6、5.7） |
| E7a | 后台任务在代理空闲时结束 | 正好唤醒 1 次，通知原文带后台任务编号，之后没有多余唤醒 | 完成通知用原生唤醒（5.5） |
| E7b 到 E7e | 模型 `job_kill`、`job/kill` 接口、归档、引擎正常退出 | 取消原因分别是模型填的原话、`cancelled by the user`、`session archived`、`owner disposed`；源码里另有 `jobs service disposed`、`jobs teardown`、`teardown` | 取消原因映射表（5.6） |
| E7f | 通知写进日志后重启 Harness | 通知仍在日志里，来源 `{kind: 'tool-jobs', form: 'notice'}`，正文带后台任务编号 | 重启后按日志去重（5.5） |
| — | 代理忙闲事件 | `agent/status` 给出 `running` 或 `idle` | 云端租约插件据此持有和释放（5.8） |

还要在实施时用同样的办法补验的：插件在进程内看到通知写进日志（`session/event`）；代理出现时补投通知；云端租约插件真实拿到和释放 InstaBox 租约（这项要用 li 或 li2 的写 key，在装机后的真机验收里做）。

两点顺带发现：rc.1 和 rc.3 每轮附带给模型的提醒原文不同（「Current runtime context…」和「<system-reminder>…」），插件不能依赖这类原文；工具输出要用标准 JSON Schema（`required` 写成数组），把 `required: true` 写在字段里会被拒绝注册。
