# 天启搬到第二台云电脑 li2：设计

状态：**等站长确认**。实现：Claude Code。

## 1. 为什么、要什么

站长北京时间 11-18 中午：「我又弄了台小芯一样的电脑，打算天启模式在这台电脑上用，和小芯的分开」。追问后定下：

- 天启换成**工具箱首页上的一个新工具**，和「世界地图」「STM32」并列；不再挤在小芯的工作台里。
- **旧数据不搬**：li 上已有的天启对话留在原处。
- **不要人设提示词**：只让它知道自己叫天启。原话：「他只在 Harness 里面工作，就相当于我直接丢用原模型」。
- **网关账号不搬**：li2 上的网关账号站长以后自己新加。
- 做法选了方案 1（§3）：同一个网站，后台给天启单独一套连 li2。

现在的情况（11-18 只读核对）：

- 天启就是小芯那台 li 上的 Harness（`dsh`）对话：和小芯共用 `~/.xin`、同一个常驻状态进程，侧边栏里混在一起（带一颗星）。
- 网站后台（`src/xin.js`）只认一台电脑：`INSTABOX_API_KEY` + `XIN_MACHINE`（默认 `li`），待送达、内核连接这些 Durable Object 都只有一份（`xin-inbox`、`xin-tasks`、`xin-backups`）。
- 天启的模型走 li 本机的 WorkBuddy 网关（`127.0.0.1:8788`，WorkBuddy2API-Hub v2.0.8，系统服务 `workbuddy-gateway`），客户端 key 在 `~/.xin/harness.key`。
- li 上的 Harness：程序在 `/data/apps/deepseek-harness`（自带 node，`@deepseek-ai/dsh` 0.2.2-rc.3），外面一层包装脚本 `~/.local/bin/dsh`，配置在 `~/.dsh`（里面有站长自己加的 purge 插件、prompt-inject 等）。
- li2：另一个 InstaBox 账号，免费版，4 核 8G，20G 盘，一次最多跑 8 小时，闲 30 分钟自动睡；模板和 li 一样（`agent-browser`，版本更新一点）。上面有 node 26、python 3.13、codex、claude、chromium；**没有** Harness、网关、`~/.xin`。

## 2. 目标、不做、不能出现的

**目标**

1. 首页多一个「天启」工具（路由 `/tianqi`），打开就是天启的聊天：对话列表、新建对话、选模型和思考强度、回话边说边出、终端动画、发文件和图片、下载它做出来的文件。体验和现在工作台里的天启对话一样。
2. 天启的一切都在 li2：对话、过程记录、状态进程、Harness、网关。和 li 互不相干：li 睡着、出问题，天启照常；反过来也一样。
3. 天启的提示词只有一句「你叫天启。」，其余是 Harness 和模型本身。
4. 和工作台同一个登录：登录一次，两边都能用。
5. 小芯的工作台去掉新建天启的入口；li 上的旧天启对话留在侧边栏，照常能看、能接着聊（在 li 上）。

**不做**

- 搬旧的天启对话；动 li 上的任何数据。
- 把 li 的网关账号、`secrets/`、用量、日志带到 li2。
- 天启的后台任务、每日任务、记事本、好感度、定时叫醒、推送提醒、备份：这些是小芯的，天启第一版都不要。
- 改小芯的行为。

**不能出现的**

- 天启的请求打到 li 上，或者小芯的请求打到 li2 上。
- li2 上跑起小芯的东西（发小芯的推送、做小芯的每日任务）。
- 网站后台日志、仓库里出现 li2 的 key。
- 改坏小芯的工作台。

## 3. 做法（站长选了方案 1）

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| **1 同一个网站，首页新工具，后台单独一套连 li2（选这个）** | `/api/tq/*` 和小芯的 `/api/xin/*` 用同一套处理，只是换成 li2 的 key、li2 这台电脑、天启自己的待送达和内核连接；页面复用工作台的聊天界面，开成「天启模式」 | 一个登录；叫醒、断线续收、流式回话、终端这些现成的都能用；一次部署两边一起更新 | 后台要从「一台电脑」改成「小芯一台、天启一台」，改动中等 |
| 2 单独一个网站 | 同一份代码再部署一份（子域名），指向 li2 | 后台几乎不用改 | 再登录一次；多一套部署、密钥、联调；子域名要在 Cloudflare 配；小芯的功能要一个个关 |
| 3 极简直连 | 网站收到一句话就叫醒 li2 直接跑 Harness | li2 上东西最少 | 叫醒、断线、刷新、历史这些都要重做一遍 |

## 4. 设计

### 4.1 网站后台：一套处理，两个「范围」

- 新路由 `/api/tq/*`，交给现有的 `handleXin`，带一个「天启范围」。范围决定：
  - 用哪把 InstaBox key：小芯用 `INSTABOX_API_KEY`，天启用新的 Worker 密钥 `TQ_INSTABOX_API_KEY`；
  - 找哪台电脑：天启用 `XIN_TQ_MACHINE`（`wrangler.jsonc` 里设 `li2`）；
  - Durable Object 用哪一份：天启用 `tq-` 开头的名字（`tq-inbox` 等），和小芯的数据分开存（内核端口令牌、钥匙、部署代号、待送达）。
- 天启范围里**关掉**的：备份、定时任务（`runCron` 只管小芯）、后台任务监督、推送订阅。请求这些回「天启没有这个功能」。
- 没配 `TQ_INSTABOX_API_KEY` 时，`/api/tq/*` 一律回「天启还没配好」，不去碰 InstaBox；页面照这个显示提示。
- 模块里按「一台电脑」写的缓存（电脑列表、`ensure` 的节流）改成按范围（或按 key、电脑号）分开，免得两边来回切换时反复查、多花子请求（免费版每个请求最多 50 个）。
- 登录：同一个站长密码、同一个登录态。
- 部署：`deploy.yml` 写密钥那一步多带一个 GitHub Secret `XIN_TQ_INSTABOX_API_KEY` → Worker 密钥 `TQ_INSTABOX_API_KEY`；没配就跳过（天启保持「还没配好」）。

### 4.2 li2 上：同一份控制器，开成「天启」

- 网站往 li2 装的是同一份控制器（`vm-agent.mjs` 和它引用的模块、内核外壳），和 li 一样走内核通道、常驻状态进程、待送达。
- li2 上的所有控制器进程都知道自己是「天启」（实现时定具体办法，比如网站给 li2 起外壳、走 exec 时都带一个环境变量，外壳存下的环境再传给状态进程和执行进程）。天启身份下：
  - 新对话、接着聊，一律用 Harness；要用 Codex、Claude 的请求直接拒。
  - Harness 的提示词只有「你叫天启。」（不再写 `tianqiPrompt()` 那一长段）；li2 上没有 purge 这类插件，不加插件配置。
  - 小芯的那些（后台任务、每日任务、记事本和好感度、空闲整理、推送、预热 Codex）不启动；相关操作回「天启没有这个功能」。
  - 清理遗留进程的定时器照常（只清自己的）。
- 状态目录还是 `~/.xin`（li2 上是新的、空的），控制器代码里写死的 `/data/home/.xin/...` 路径在 li2 上同样成立（同一个模板，同一个用户 `box`）。

### 4.3 天启页面

- `site/tools.js` 加一项：`id: 'tianqi'`，名字「天启」，`path: '/tianqi'`，`src: '/tools/tianqi/'`，图标用天启的星。分类放「工具」。
- `site/tools/tianqi/index.html`：加载 `/xin/chat.css`、`/xin/term.js`、`/xin/chat.js`，在加载 `chat.js` 之前写一份配置（接口前缀 `/api/tq/`、身份天启），打开就是全屏的聊天，不需要首页那个小芯岛。
- `chat.js` 认这份配置：
  - 所有接口（包括上传、文件、预览、流）走 `/api/tq/`；
  - 标题、标志、输入框提示都是天启（深蓝底、像素星，沿用现在的天启样式）；
  - 新对话固定 Harness，没有「小芯 | 天启」切换；保留选模型和思考强度；
  - 不显示小芯的东西：后台任务、每日任务、用量页里的谷歌额度、备份、小芯的表情和动作；
  - 「还没配好」「网关还没配好」两种情况，聊天区直接写清楚、不让发。
- 小芯的工作台：去掉「新建天启对话」按钮、空白页上的「小芯 | 天启」、命令面板里的「新建天启对话」。旧的天启对话照常显示、能接着聊。

### 4.4 li2 的一次性准备（代码上线后做，站长已同意叫醒 li2 看过）

全部用 li2 的 key 经 InstaBox 执行，过程写进交接记录；不碰 li。

1. Harness：把 li 上 `/data/apps/deepseek-harness` 的**程序**装到 li2 同一个位置（同一个版本 0.2.2-rc.3），写一个不带 purge 那几行的包装脚本 `~/.local/bin/dsh`，`~/.dsh` 从空开始，只放 headless 配置（网关线路由控制器每轮写）。li 上 `~/.dsh` 里的插件、prompt-inject、红队配置都不带过去。
2. 网关：把 WorkBuddy2API-Hub v2.0.8 的**程序文件**和 `workbuddy-gateway.service` 装到 li2（同样只听 `127.0.0.1:8788`）。`accounts/`、`secrets/`、`usage/`、`logs/`、`backups/` 都不带；服务先装好，等站长加账号。
3. 站长在 li2 的网关里加新账号以后告诉我，我把网关给本机客户端的 key 写进 li2 的 `~/.xin/harness.key`（权限 600，不打印、不进仓库），然后发一句真话试试天启能不能回。
4. GitHub Secret：站长在仓库 Settings → Secrets and variables → Actions 新加 `XIN_TQ_INSTABOX_API_KEY`，值就是这次给的 li2 key；下一次部署写进 Worker。

## 5. 测试

- 网站后台：
  - `/api/tq/*` 走 li2 的 key 和电脑，`/api/xin/*` 还是 li，两边的 Durable Object 名字不同、互不读写；
  - 没配天启 key 时回「还没配好」，一个 InstaBox 请求都不发；
  - 天启范围里备份、定时任务、后台任务监督都关着；
  - 给 li2 起外壳、走 exec 都带上天启身份。
- li2 控制器（天启身份）：
  - Harness 的提示词正好是「你叫天启。」；
  - 要 Codex、Claude 的请求被拒；小芯专属的操作回「没有这个功能」；
  - 小芯身份下一切照旧（现有测试全过）。
- 页面（浏览器测试 + 截图）：
  - 首页有「天启」，打开是天启模式，请求都发到 `/api/tq/`，看不到小芯的东西；
  - 「还没配好」「网关还没配好」的提示；
  - 小芯工作台里没有新建天启的入口，旧天启对话还在；
  - 截图：电脑 1280、平板 1024 和 768、手机 390，浅色、深色。
- 正式站联调：小芯那一套不变。天启在配好以前只核对「还没配好」的回答；配好以后加一句真对话（不进这次的上线门槛）。

## 6. 上线顺序

1. 代码一个 PR：后台两个范围、li2 天启身份、天启页面、工作台去掉入口。上线后天启页面显示「还没配好」，小芯不受影响。
2. 站长加 GitHub Secret；重新部署一次（或下一次正常部署）写进 Worker。
3. 我准备 li2（§4.4 的 1、2）。
4. 站长加网关账号 → 我接上 key（§4.4 的 3）→ 发一句真话验收。

## 7. 风险

| 风险 | 对策 |
|---|---|
| 改共用的后台，弄坏小芯 | 小芯的现有测试、浏览器测试、正式站联调全过才上线；天启的改动都挂在「天启范围」下 |
| `chat.js` 多了一种模式，分支变多 | 天启模式只认一份配置，集中在少数几处判断；浏览器测试两种模式都跑 |
| li2 是免费版，有时长上限、会自己睡 | 和 li 一样：叫醒中有提示，冷却期间有提示 |
| WorkBuddy2API-Hub 是非官方客户端，README 写了上游在收紧、账号可能被风控 | 站长自己的选择；网关账号由站长自己加，我们不碰账号 |
| 这把 li2 key 是全部权限、永不过期，在聊天里给过 | 不进仓库、不进日志；建议以后在 InstaBox 里给网站另开一把权限小一点的 |

## 8. 留给实现时定的

- 天启身份具体怎么传到 li2 上的每个进程（环境变量的名字、外壳怎么存）。
- `chat.js` 天启模式的配置格式、哪些界面元素要藏。
- Durable Object 名字前缀、缓存怎么按范围分。
- li2 上 Harness、网关程序的具体装法（复制哪些文件、权限）。
