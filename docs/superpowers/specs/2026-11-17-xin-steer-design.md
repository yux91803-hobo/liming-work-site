# 小芯：后台干活时插话、补充接回原任务、主动回来说一句（2026-11-17）

站长 2026-11-17：「我想让小芯在后台做事时，我还能在原聊天里跟它聊别的，也能随口补一句，调整刚才交代的事。」具体三件：

1. 补一句，小芯能接在原任务上。例：让它查电脑上有哪些 Agent 模型，查到一半说「刚才查模型那件事，备用的别列，只查实际启用的」。听得出指哪件事就接过去，几件都对得上才问；顺手聊别的就正常聊，后台照常做；那件事已经做完或停了，先说状态，等站长明确说继续再接着做。手头已经开始的操作可以做完，还没开始的按新要求判断，前面查到的也要重新筛一遍。
2. 学 Muse Code 的插话：小芯自己知道这句补充是进了当前这一轮，还是要等这一轮结束；回话顺着对话说一次，不先说「已记下」再说「已送进当前轮」。嘴上应了、还没落实就碰到超时、额度用完或重启，恢复后照样带上；断线重送只算一次；旧的那一轮晚回来，不盖掉后来的要求和进度。
3. 学个人版 Muse 什么时候主动回来：发现会改变结论的事、碰到会改变计划的阻塞、要站长拿主意时回原聊天说一句；平常读了哪个文件、做到第几步不说（工作台看得到）；相关的合成一条；准备发的时候看还有没有用，最终结果先到了就不发。

站长说「具体怎么做你结合现有架构判断」，下面是按现有架构定的做法。

## 参考

- Muse Code [Working with the agent](https://dev.meta.ai/docs/muse-code/interactive)：Enter 是 steer，「inject into the turn in progress. The agent applies it on its next step」；Alt+Enter 是 queue，「hold your text for the next turn」。
- Muse Code [Coordinate sessions with messages](https://dev.meta.ai/docs/muse-code/session-messaging)：默认「steers the recipient's active turn when possible」，在「its next safe model step」加进去；做不到就「Queue for the next turn」；「duplicate message IDs are deduplicated」。
- Muse Code [changelog](https://dev.meta.ai/docs/muse-code/changelog) 1.4.16：插话没成时不再提示「steer failed」，「it stays queued and is delivered once」；1.4.12：崩溃后排着的消息不当成已经做了；更早的版本：重启后先送崩溃前排着的消息。
- Meta [Introducing Muse](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)：「comes back when something changes or when it needs approval」；[How we designed Muse](https://muse.ai/blog/how-we-designed-muse)：「notifies you only when something is meaningfully new or needs your input」「the bar for sending one has to be high」，平时做什么在头像下面的活动记录里看。
- OpenAI Codex `codex-rs/core`：`turn/steer` 把输入放进正在跑的这一轮；这一轮收尾时还有待处理的输入就不结束，接着处理（小芯的 Gemini 后台照这个做）；`input_queue.rs` 补充一次取完、和下一轮一起交出去（小芯 11-12 已采用）。
- opencode `subagent-completion.ts`、Codex `world_state` 只发变了的部分：前台不每轮列「进行中」（#117 的教训），这次也不恢复。

## 现状（改之前）

- 前台用 `xin task tell 编号 话` 转补充。在做的 Codex 任务走 app-server 的 `turn/steer`；Gemini（Antigravity）任务只能放进收件箱，整轮做完才再起一轮按补充改。
- tell 一调用，前台这一轮就结束：Gemini 前台的回话是调用前就写好的，DeepSeek 前台没写就要一句；两者都不知道补充是进了当前轮还是要等。
- 前台每轮不带进行中的任务，要补充得先 `xin task list` 查编号。
- 做完、停了的任务收到 tell 会直接重新开工。
- 补充的耐久性有缺口：断线重启后续做的那一轮不带收件箱里的补充，要等它做完再起一轮；停下会清空收件箱；Gemini 额度用完、卡住换模型时，新模型不知道补充；网页任务详情里补充不带 clientId，重发会算两次。
- 后台只有 ask（要站长批准，问完这一轮就结束），没有「说一句、接着做」。

## 设计

### 1. 补充送进哪一轮（控制器）

- **能不能进当前轮**由这一轮的执行方式决定：Codex app-server 的轮次、Gemini 后台的轮次可以（`steerable`）；模型这一步已经做完、在做网页检查或编译核验时，或者执行方式不支持时，只能排到下一轮。
- **Gemini 后台每一步之间接补充**（`antigravityWork`）：每次请求 Gemini 之前，从这一轮的记录里取出没送过的补充（`steer_take`，在 tasks 锁里标成已送达，不会送两次），放在这次请求的最前面：「兄弟刚补充了要求（按先后，以最后一条为准）：……正在跑的命令照常做完；还没做的步骤按新要求重新判断；之前查到的结果也按新要求重新筛一遍；最后给的结果只按新要求。」
- **交结果前再看一眼**：Gemini 交了 final（或问了问题），但这时又有新补充，就不结束，把补充交给它再走一步，最多 3 次（像 Codex 这一轮还有待处理的输入就接着处理）。
- 补充在这一轮的终端里显示成兄弟的一句话（和前台插话同样的 `user` 事件），工作台看得到它进了哪一步之前。
- **tell 的回执带 `delivery`**：`now`（进了正在做的这一轮，下一步就按新要求）、`next`（这一轮跑完再按补充接着做）、`start`（还没开始，并进要求）、`resumed`（明确继续以后重新开工）。Codex 插话失败（比如这一轮刚好收尾）时照 Muse Code 1.4.16，不报错，留到下一轮，只送一次。

### 2. 补充不丢、不重复、不被旧的盖掉

- 补充记在这一轮的记录里，有编号：`pending`（还没送）→ `accepted`（模型收到了）或 `next`（这一轮接不了）。
- 这一轮正常做完：收到了的已经用上；没送进去的照旧带到下一轮接着做（已有）。
- 这一轮**没有正常做完**（超时、断线、重启、停下、连接出错）：这一轮收到的补充**全部**带到下一轮——没法确定模型已经照着做了。下一轮开头写「兄弟之前补充过（按先后，以最后一条为准）」。重启后自动续做、临时出错后等一会儿续做、兄弟说继续以后续做，都带上。
- **同一轮里换模型接着做**（Gemini 额度用完、卡住）：新模型从头开始，所以把这一轮所有补充一起交给它。
- **停下不再清掉补充**：补充是要求，不是操作；兄弟之后说继续，照样按补充做。
- **断线重送只算一次**：tell 带编号，同一编号第二次来直接返回第一次的结果。网页任务详情里的补充也带 clientId（内核按 `task_tell:clientId` 记回执，网站可以放心重试）；前台同一轮重放同一个 tell，内核已有 `front:run:argv` 回执。
- **旧的那一轮晚回来**：任务只认最新一轮（已有 `lastRun` / attempt 检查）；补充按时间排，以最新为准。

### 3. 前台：听出是哪件事，回话顺着说

- **只在相关时附 `<手上的事>`**：兄弟这句话和这个对话的某件事有关时，在他的原话前面附一块：这个对话里没做完的任务，加 2 小时内做完、停下的，最多 6 件；每件写编号、标题、状态、补充现在怎么接（「补充能接进正在做的这一轮，它下一步就按新要求来」/「这一轮中途接不了，要等这一轮跑完再按补充接着做」/「已经做完了 / 停了：兄弟明确说继续才接着做」）。
  - 「相关」：这句话和任务标题、原话有两个以上相同的两字词或一个相同的英文词，或者带补充、改主意的说法（刚才那件事、别列、改成、只要、算了……）。判断宽一点没关系：附了只是给前台对照，补不补由它按内容判断；没附时前台可以 `xin task list`。
  - 和以前一样，不相关的时候不附：#117 的教训（每轮都带进行中，DeepSeek 会把任何一句都答成进度）不重犯。
- **规则**（`vm-persona.mjs` 前台「手上的事」）：
  - 对得上一件就 `xin task tell` 那件；几件都对得上，才问一句是哪件；明显在聊别的就正常聊，后台照常做，不提进度。
  - 那件事已经做完或停了：先告诉他现在的状态和要点，问要不要接着做；他明确说继续，才用 `xin task tell 编号 --continue 话`。不带 `--continue` 的 tell 碰到做完、停了、没做成的任务，控制器不重新开工，回执给出状态，前台按回执说。完成事件里让原工作接着改（已有预算）和网页任务详情里的「接着做」不受影响。
  - 回话只说一次、顺着说：能进当前轮的，像「行，最后只给你列正在用的」；要等这一轮的，像「这轮跑完我就按你补的范围再核一遍」。不报编号，不先说记下了再说送进去了。
- **回话和实际接法对得上**：Gemini 前台一次就把回话和调用一起写好；附了 `<手上的事>` 时它是照着快照里写的接法写的。控制器在 tell 时算出实际接法，和快照里写的一样就用它预先写好的话；不一样（比如任务刚好做完了），不用那句，带着实际回执再要一句（`ownWords` 也带上 `delivery`）。

### 4. 后台主动回原聊天说一句

- **后台的新动作**：Codex 任务 `xin task note 一句话`（经任务桥）；Gemini 任务 action=note。说完接着做。
- **什么时候说**（后台提示词）：只在发现会改变结论的事（「两份配置写的默认模型不一样，我再核一下实际启动的是哪个」）、碰到会改变计划的阻塞时说；要兄弟拿主意的照旧用 ask。读了什么文件、做到第几步不说，工作台看得到。相关的发现攒成一条再说。门槛要高。
- **控制器**：
  - 记进任务的 `notes`，按 note 的编号去重。
  - 20 秒内同一任务后面的 note 合成一条。每件任务最多 3 条，超了只进终端。
  - 发之前看还有没有用：任务已经做完、停了、没做成，或者结果已经在排队要告诉兄弟（交接已入队）就不发，只进终端。
  - 这个对话正在回兄弟的话时，等它说完再发；发之前再查一次。
- **发法**：直接作为小芯的一条消息放进原聊天（不再过一遍前台模型）：网页和前台以后的历史里都看得到。走现有的完成交接队列（`handoffs` 表，kind=note），交接队列已经有「对话空闲才发」「任务版本变了就作废」。不推送到手机，最终结果照旧推送。

## 不做的

- 不每轮把进行中的任务塞给前台。
- 不让后台的 note 经前台模型改写（多一次模型调用、可能答偏）；note 本来就是小芯第一人称写的。
- 不加「模拟断电」的线上接口：正式站联调用「停下再继续」代替真实断线，进程被杀、超时、换模型在本地测试里用真进程验证。

## 验证

- 单元测试（先写，先失败）：
  - Gemini 假 agy：两步之间收到补充，下一次请求最前面带着；final 时有新补充，再走一步。
  - tell 回执的 `delivery`：now、next、start、resumed。
  - 不带 `--continue` 的前台 tell 碰到做完、停了的任务：不重开，回执给出状态。
  - 超时、断线重启、停下、换模型以后，下一轮（或换的模型）带着补充。
  - 同一 clientId 的 tell 只算一次。
  - `<手上的事>` 只在相关时附；无关的一句没有。
  - note：合并、上限、任务做完以后不发、对话忙时等。
- 浏览器测试：note 显示成小芯的一条消息；任务详情里补充带 clientId。
- 正式站联调（`scripts/test-xin-live.py`，真模型）：
  - Gemini：按顺序核对 4 个名字（2 个启用、2 个备用）。第一步开始后在聊天里补「备用的别列」。检查：
    - 前台回的是自己的话，不是固定句；
    - 补充进了同一轮；
    - 之后的命令没有再处理备用的；
    - 最终名单只有启用的。
  - 停下再继续：补充以后把任务停下。先只说一句不带「继续」的话，前台应该说状态、不开工；再说继续，接着做的那一轮带着补充，最终名单对。
  - Codex：点名 Kimi 做同样的任务，补充经 `turn/steer` 进当前轮，最终名单对。

## 实际做成的样子（和上面不一样的地方）

- **`<手上的事>` 只认说法，不看词重不重合**：上面写的是「两个以上相同的两字词或一个相同的英文词，或者带补充的说法」。对照正式联调发现，「只回复 陀螺 茶壶 贝壳，不要执行命令，也不要等待后台」和派活原话共用「回复、后台、执行、等待」，按词重合会附上，正好重演 #117。所以只认说法（`vm-steer.mjs` 的 `mentionsWork`：刚才、那件事、别列、只要、改成、继续、停下、进度……），没附时前台可以 `xin task list`（列表里也带每件事补充现在怎么接）。
- **前台的回话**：Gemini 前台一次返回文字和调用。控制器把附上的快照里每件事的接法记进这一轮（`frontHandModes`），tell 的实际接法和它一样（或快照写「已结束」、兄弟说了继续）才用预先写好的话；不一样、或者没附快照，就带着回执（`delivery` 和说明）再要一句。兜底的固定句也按接法分开说。
- **已结束的任务**：前台不带 `--continue` 的补充记进收件箱、不开工，回执不结束这一轮（前台接着说状态、问要不要接着做）；兄弟之后说继续，这句补充跟着一起交出去。
- **note 的合并**：从第一条起 20 秒内同一件事后面的合进同一条（存在交接队列那条记录里）；每件事最多 3 条按条（合并的算一条）计。
- **note 的显示**：不经前台模型，原对话里直接记一轮说完的话；网页靠 `tasks` 接口带回的 `notes` 画在最后，终端里写「告诉兄弟：…」。兄弟中途的补充在终端里是一行「> …」。
- **正式站联调**：三段都按上面做了，补充用站长的原话「备用的别列，只查实际启用的」（写成「只列」的话，模型可以照样把备用的查一遍、只是不列，「之后的命令不再处理备用的」就会误报）。Gemini 那一段先在聊天里补，检查的是前台转来的那句（编号 `ft-` 开头）之后还核不核对备用的（只看 `echo 名字 >> checked.txt` 这样的核对命令：按新要求把查过的筛掉时命令里也会带着名字，那是要的「重新筛一遍」）；再用同一编号直接补同一句、重送一次（回执都是「进了当前这一轮」，过程里只出现一次）。每一步先睡 30 秒（停下再继续那一段 40 秒），前台那一轮说完时任务一定还在做。联调这一步时限 35 → 45 分钟。
