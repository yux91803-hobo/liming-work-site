## 1. 为什么

站长原话：「你觉得legacy有必要么……我感觉没啥必要呢，还搞得那个bug一直修不好」。

正式站实况（只读下载云电脑上的 `~/.xin/logs/kernel.jsonl`，11-16 零点到 11-17 22:18）：

- 3240 次操作走常驻状态进程，50 次没走。这 50 次全部出现在换版本的那一刻：新版本的控制器还没装上（`agent_missing`，409），装上以后外壳临时起一个控制器进程来做。这个进程看到旧的状态进程还活着，就把请求转交给它。所以这 50 次大多也是状态进程写的，不是老路自己写库。
- 换版本时，从旧状态进程收到停止到新状态进程准备好：10 次里一般 0.2–2 秒，最长一次约 6 秒（11-16 20:00，旧进程用了 4 秒收尾，新进程 1.4 秒起好）。
- 也就是说，旧模式在正式站上基本没有真正派上用场，却要求每处改动在两种模式和两种模式之间的切换下都对：控制器测试跑两遍；出过只有旧模式才有的 bug（#162：两个进程同时派发同一轮，正式站碰不到，却让检查挂了）；#166 那类「状态进程被杀以后切回旧模式」的问题也是因为要来回切换。

删掉它**修不好**「Gemini 后台主动说一句」那条偶发失败：那条只在常驻进程模式那一遍挂过。这一点已经和站长说清楚。

## 2. 目标、不做的、不能出现的

**目标**

1. 写状态的只有常驻状态进程一个。其他进程（每轮的执行进程、`xin` 命令、exec 进来的控制器入口）只转交，从不自己写库。
2. 删掉：`lockedCall` 里的 `flock` 业务锁那条路、看门狗进程、所有权记录的 `legacy` 模式和来回切换（`owner-legacy`、`release` 交回 legacy）、外壳 `/xin/op` 和 `/xin/stream` 每次请求起一个控制器进程的路、Worker 的 `XIN_STATE_OWNER` 开关。
3. 控制器测试只跑一种：都对着真的状态进程跑。`npm run test:kernel` 并进 `npm run check`，CI 少一步。

**不做**

- 第 3 批 B 的收尾暂存、宿主授权、凭据代理、第 5 批的五处「读了再写」、拆重活。
- exec 传输照旧留着（`XIN_TRANSPORT`）：内核端口不通时 Worker 还能经 InstaBox exec 跑控制器入口，入口只转交给状态进程。
- 每轮一个执行进程、执行进程的 `flock -n` 轮次锁（保证同一轮不会有两份）、空闲整理的启动锁都不动，它们不是旧模式的业务锁。
- 工作台界面不动。

**不能出现的**

- 删用户数据、改数据格式。对话、记忆、任务记录、待送达都不动；`owner.sqlite` 里已有的记录照读。
- 两个写者同时写（状态进程不在时，别的进程悄悄自己写）。
- 丢消息：状态进程暂时不在时，网页发的消息照旧留在 Worker 的待送达里重试。
- 状态进程重启以后派发、到点交接、通知停住不动（状态进程启动时照旧完整扫一遍）。

## 3. 状态进程不在的时候怎么办（这次唯一要定的事）

旧模式现在的用处只剩这一个：状态进程不在时（换版本那一两秒、被杀以后到重启之间），别的进程可以自己写。删掉以后要有替代。比较过三种：

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| **A 等它好（推荐）** | 外壳和其他进程都等状态进程准备好；等不到就回「主人暂时不在，没执行，可以重试」，Worker 的待送达稍后重试 | 最简单；只有一个写者；和 gRPC 的 wait-for-ready 一样（grpc/grpc `doc/wait-for-ready.md`：通道没好时把请求排队，好了再发） | 换版本那一下发的消息多等一会儿（实测一般 0.2–2 秒，最长约 6 秒）；状态进程彻底起不来时小芯停摆，直到修好或回滚 |
| B 换版本时转给旧进程 | 新版本的状态进程没好之前，外壳继续起一次性控制器进程，把请求转交给旧的状态进程 | 换版本那一下不用等 | 「每次请求起一个控制器进程」这条路得留着，删不干净 |
| C 控制器入口自己拉起状态进程 | 像 Bazel 的客户端那样：没有状态进程就自己起一个 | 外壳挂了也能用 | 谁来起状态进程变成两处，多一套「谁先起来」的规则；正式站已经有 systemd（`Restart=always`）和 Worker 的 `ensure` 在看着外壳 |

选 A。B 和 C 都是为了省那几秒，却要多留或多写一套机制，和「删干净、只留一条路」的目的相反。

状态进程彻底起不来的兜底：

- 新版本起不来，上线时的正式站联调会发现，Actions 自动回滚到发布前记录的版本（回滚以后照常用常驻进程模式，数据格式不变）。
- 状态库每天照旧导出一份备份（留 7 天）。
- 用量页照旧显示「常驻进程在管」和这次运行了多久，健康检查照旧报谁是主人、切换次数。

## 4. 设计

### 4.1 所有权

- `owner.sqlite` 的独占锁和切换次数（epoch）照旧：状态进程启动时拿独占锁，一直不放；被 `kill -9` 时锁随进程释放。
- 以后只写「归内核管」。读到空记录或旧版本写的 `legacy`：当作「现在没有主人」，状态进程照常接手（接手前照旧做一次 `VACUUM INTO` 备份）。不回写 `legacy`。
- 判断规则只剩两行：拿共享锁 busy → 主人在，交给它；拿得到 → 主人不在，**不写**，按 §4.2 等一会儿或回「主人不在」。

### 4.2 不是主人的进程

- `lockedCall`、`journal.write`、`journal.append`：一律经套接字交给状态进程（现在内核模式就是这样）。删掉 `flock` + 子进程那条路，以及「旧模式下拿可写句柄」的那一下。
- 主人不在时：在原有的等待预算里重试（#166 定的报告预算、前台的 30 秒），用完回 `owner_unavailable`（没执行，可以重试），调用方按现有规则处理。不新开等待规则。
- 读库照旧用只读句柄。

### 4.3 外壳（`vm-kernel.mjs`）

- `/xin/op`：只走状态进程。请求要的版本和正在跑的不一样，或者状态进程正在起：看护者照旧切版本、等它准备好（`readyWaitMs` 现在就是 15 秒）；还没好就回 503 / `owner_unavailable`（没执行），不再起控制器进程（删掉 `runAgent` 这条路和 `maxConcurrent` 计数）。
- `/xin/stream`：轮询照旧交给状态进程；状态进程不在就发 `error` 事件，网页照旧退回轮询。
- 换版本：旧状态进程收到 `release` 后，做完手上的、刷完投影就放锁退出，**不再把记录改成 legacy**。新状态进程已经在等独占锁，拿到就接手，切换次数加一。删掉 `owner-legacy` 和「退出后用 owner-legacy 补上」。
- 被杀：锁已经释放，看护者照旧重新拉起；这段时间的请求按上面等或回「主人不在」。

### 4.4 看门狗

- 删掉看门狗进程（`ensureWatchdog`、`watchdog` 命令、换版本时的 `flock … watchdog` 重启、`LONG_LIVED` 里的 `watchdog`）。它的循环（`recover`、`dispatchLaunches`、`tickTasks`、`pumpHandoffs`、通知、回调）第 2 批起就在状态进程里跑。
- 空闲整理（`memory-idle`）的启动方式不变。

### 4.5 Worker

- 删掉 `XIN_STATE_OWNER`（`wrangler.jsonc` 的变量和 `src/xin.js`、`src/xin-kernel.js` 里的读取）；发给外壳的期望固定是常驻进程模式。`src/xin-kernel.js` 现在没配置时默认 `legacy`，要改成固定 `kernel`。
- 「主人暂时不在」照旧是可以放心重试的结果；待送达按临时错误重试，网页显示「已收到 · 唤醒中」。

### 4.6 换成新版本那一次

- 正式站现在的记录就是「归内核管」，上线时和平常换版本一样：旧状态进程放锁，新状态进程接手。
- 自动回滚到上一版：上一版还带着旧模式，但正式站的配置是常驻进程模式，它照常接手；数据格式没变。

## 5. 测试

- **所有控制器测试都对着真的状态进程跑。** `test/helpers/state-mode.cjs` 现在要 `XIN_TEST_STATE_MODE=kernel` 才起状态进程，改成总是起；还没接这个帮手的测试接上。`scripts/test-xin-state-mode.mjs` 和 CI 的「常驻状态内核复用控制器行为测试」那一步删掉，`npm run check` 一遍就够。
- **只测旧模式手段的测试**（`flock` 包装、legacy↔kernel 切换、看门狗）：换成测同一个保证的行为测试，PR 里逐条写明删了哪条、换成哪条：
  - 只有一个写者：状态进程不在时，别的进程不写库，回「主人不在」；状态进程回来以后同一个请求重试成功、只执行一次。
  - 换版本：旧进程放锁、新进程接手，期间的请求等到或回「主人不在」，不丢、不重复执行。
  - `kill -9` 状态进程：执行进程照常把这一轮做完（在报告预算内等到新主人），派发和到点交接在新主人起来后接着走。
- 写者清单测试（`test/xin-writers.test.cjs`）照旧防止新长出直接写库的地方。
- 每个 PR：`npm run check`、`npm run test:e2e` 全过；CI、测试站、正式站联调全绿才算完。

## 6. 分三步上线

| 步 | 做什么 | 线上行为变不变 |
|---|---|---|
| 1 | 测试全部对着真的状态进程跑（§5 第一条）；`test:kernel` 并进 `check`。先把哪里还暗中依赖旧模式全翻出来。只测旧模式手段的那几个测试到第 3 步再换，在那之前照旧不起状态进程 | 不变（只改测试） |
| 2 | 状态进程不在时改成「等它好、等不到回主人不在」（§4.1–4.3）；换版本不再交回 legacy；Worker 去掉 `XIN_STATE_OWNER` | 变：换版本那一下多等 0.2–6 秒 |
| 3 | 删掉已经走不到的代码：`flock` 业务锁那条路、看门狗、`owner-legacy`、外壳的 `runAgent`；旧模式专用测试按 §5 换成行为测试；文档 | 不变（删的是走不到的代码） |

每一步单独可回滚。第 2 步上线后，从云电脑的内核记录核对换版本那一下的等待时间。

## 7. 风险

| 风险 | 对策 |
|---|---|
| 换版本那一下发的消息要多等 | 实测一般 0.2–2 秒，最长约 6 秒；超过 6 秒待送达先回「已收到 · 唤醒中」再取，不丢 |
| 状态进程彻底起不来，小芯停摆 | 上线联调 + 自动回滚；每日状态库备份；健康检查和用量页能看到 |
| 某个不常用的操作其实还靠旧模式自己写库 | 第 1 步让全部测试对着状态进程跑，先暴露出来；写者清单测试兜着 |
| 改的是核心，改动本身出错 | 分三步，每步全量测试 + 正式站联调；第 1、3 步线上行为不变 |

## 8. 留给实现时定的

- 状态进程不在时，各类调用等多久再回「主人不在」：沿用现有预算，不新开。实现时列出每个入口用的是哪个预算。
- 第 1 步里每个测试文件怎么接状态进程（直接用 `stateClient`，还是在公共的 `lockedSpawn` 里起），以改动最少为准。
- 第 3 步删代码的先后顺序，以每次提交都能单独跑过全部测试为准。
