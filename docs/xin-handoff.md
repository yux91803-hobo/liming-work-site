### 4.2 记忆 v1 第 2 件：空闲整理（设计：`docs/xin-next-stage.md` §4.3、§4.4、§4.7、§4.10）

本阶段已实现并合并（#93；正式站状态见对应 Deploy）：`vm-memory-idle.mjs`，默认安静 45 秒；轻整理 600 字 / 2 轮，深整理 4,000 字 / 一周；每天 4 次 / 48,000 token，65 秒请求时限。每个对话的 run / event / offset 断点在 `memory_meta`，模型请求前持久预留预算。结果统计在 `idle_last`，最近尝试时间在 `idle_attempt`，不记原话或模型输出日志；`memory_versions` 留版本，`restoreMemoryVersion` 可显式回退；忘掉会清除关联版本。

目标：从默认模式的真实对话里提出记忆，并更新已有判断。

- **时机**
  - 一段对话安静下来、新内容够多时做「轻整理」，只处理新内容。
  - 积累够多或超过一周时做「深整理」。
  - 只在电脑本来就醒着时运行，不为整理叫醒电脑、不续活动租约（`XinTaskSupervisor` 和 `tasks-lease.json` 不动）。
  - 有用户消息或后台任务时让开；被打断后从断点继续。断点是每个对话处理到的 run，存 `memory_meta`。
- **防编造**
  - 模型（前台同款 DeepSeek，经 `CODEX_ROUTE` 网关）只能「提议」，每条提议必须带原话片段和出处 run。
  - 控制器逐字核对引文确实出现在那一轮的**用户原话**里，不符就丢。
  - 后台任务、网页内容、天启对话不能产生关于站长的记忆。
- **判断规则**
  - 明确说的（stated）立即生效。
  - 观察到的（observed）在不同日子、不同话题出现到阈值才生效。建议默认：2 个不同日期的证据。
  - 推测（inferred）只进待确认。
  - 站长的纠正立即取代旧判断，旧的留历史（需要加「已取代」状态或取代关系，**只能加表或加列，不能删已有数据**）。
  - 碰到 `memory_forgotten` 里的内容一律跳过。
- **上限**
  - 每天次数和 token 有上限；每次一两分钟内。
  - 一次深整理能改动的条目有比例上限，超过的留给站长确认。
  - 每次改动写 `memory_log`，可回退。
- **网页**：「小芯的记忆」上待确认的新提议要能看出来自哪段对话（现有出处链接已支持）。

## 6. 经验和坑

- **分支**
  - 每次从 `origin/main` 开（或重开）`claude/...` 分支。
  - 强制推送会被权限拦下。分支已有合并过的旧历史时：`git checkout -B <分支> origin/main`，提交，然后 `git merge -s ours <旧分支头>`。确认 `git diff HEAD^1 HEAD` 为空后再普通推送。
  - PR 用 squash 合并。
- **本地验证**
  - `npm run check`：语法、资源引用、全部单元测试。
  - `npm run test:e2e`：需要先 `npm run dev` 起 5173 端口的预览，并设 `CHROMIUM_PATH=/opt/pw-browsers/chromium-*/chrome-linux64/chrome`。
  - 改了页面要截图自查：电脑 1280、平板 768 和 1024、手机 390，浅色和深色。
- **部署流水线**：只改文档也会触发完整部署和真机联调（`deploy.yml` 没有路径过滤），尽量把文档和代码放在同一个 PR 里。
  - 节省 Actions：PR 完整验证后保存 `tested-tree-check/e2e` 两份代码树证据（7 天）；main 的正式发布只有在同仓库已合并 PR 的成功运行里找齐证据，且目录树、head 和运行号全部一致时才复用测试。缺证据或不同代码会停止发布；手动 workflow 仍完整测试。正式站冒烟和真机联调照常，不能拿失败的测试结果复用。同一个 PR 更新会取消旧 SHA 的验证，发 PR 前先在本地测完、把相关修复集中提交。

- **真机联调**：用真实模型、站长的正式账号，失败会自动回滚。脚本约定不在 CI 日志里输出模型过程、响应正文或截图。
- **对时间敏感的测试**
  - CI 机器忙时，测试里很短的超时会误判。例如 #91：`XIN_DEAD_MS=300` 时，新启动的进程还没写 pid 就被当成断了。
  - 修法是放宽时间、不改判断内容。确认方法：在本机用 `node -e "while(1){}"` 占满 CPU 复现，并和改动前的版本对比。
- **InstaBox 免费机冷却**
  - `maxRunMinutes=120`：连续运行满 120 分钟会被强制冷却，期间叫不醒。2026-11-08 这次约 3 分钟；按 InstaBox 文档，后续冷却可能从 5–20 分钟起逐次加长。
  - 部署联调和 exec 排查会让电脑一直醒着，少调 exec。联调第一步失败、电脑上又没有新记录时，先只读查看 `GET /v1/machines/{id}` 的 `cooldownUntil`、`runStartedAt`，不要先反复执行命令或叫醒。
  - 正式站联调调用真实模型，偶发失败会自动回滚；先查清原因，确认和改动无关后，才重跑失败 job。
- **云电脑**
  - 会话里有 `INSTABOX_API_KEY` 时可以用 InstaBox API 只读排查：`POST https://api.instabox.sh/v1/machines/{id}/exec`，body 为 `{cmd, timeoutSeconds}`；机器 id 从 `GET /v1/machines` 拿。
  - 调用前先读 https://instabox.sh/llms.txt 。
  - 删机器或快照前必须先问站长。
  - 控制器数据在 `~/.xin`：`workflow.sqlite`、`sessions/`、`runs/`、`memory.md`、`agent/`（Worker 上传的模块，按内容摘要命名）。
- **隐私**：站长的记忆、旧记事本和聊天内容只在必要时看，能只统计数量就只统计。之前的排查都只数了条数，没读内容。
- **模块上传**
  - Worker（`src/xin.js` 的 `agentScript`）从 `vm-agent.mjs` 起，按 `from './vm-xxx.mjs'` 递归上传本地模块，并按内容摘要改名。
  - 新模块必须用这种写法被引用；文件名要匹配 `vm-[a-z0-9-]+.mjs`。
- **回滚兼容**
  - 正式站随时可能回滚到上一版 Worker，云电脑的数据和数据库结构不会跟着回去。
  - 数据库改动只能加表、加列，旧代码要能忽略。
  - 旧版本可能还在写的文件（如 `memory.md`），新版本要能接着处理。
- **网页 op**：网页用到的每个 op 都要同时在 `src/xin.js` 的 `OPS` 和 `vm-agent.mjs` 的 ops 里登记，有测试会检查。
- **文档**：每次改动在 `docs/CHANGES.md` 最上面加一条；功能变了顺手更新 README；`docs/xin-next-stage.md` 第 7 节的进度行跟着更新。
