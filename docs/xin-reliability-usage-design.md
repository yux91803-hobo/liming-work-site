## A. 后台可靠性（PR 1）

### A1 每日任务用自己的目录

- 现状：每日任务的目录是整个 WORK（`vm-agent.mjs:1441`），调度规则「目录有包含关系就不同时跑」（`:1515`）让它和所有后台任务互相排队，最长 180 分钟。
- 做法：每日任务的目录改成 `WORK/daily/`，开工的工作目录也用它（`startTask` 的 `cwd` 取 `t.dir`）。权限不变（仍完全放权），它照样能按绝对路径访问别处。
- 已经在跑的旧每日任务记录着 `dir: WORK`，跑完就不再影响。
- 参考：opencode `run-coordinator.ts`（按键串行、不同键并发）——只有真冲突的才排队。
- 测试：每日任务在跑时派一个普通任务，普通任务立刻开始；同一个目录的两个任务仍然排队。

### A2 临时错误：控制器自己等一会儿接着做

- 现状：模型开始干活后，一轮失败就算任务「没做成」（`canSwitch` 只管没开工的情况，`vm-agent.mjs:708`），续不续交给前台模型（最多 2 次、不等待）。
- 做法：
  1. 新模块 `vm-retry.mjs`，一个纯函数判断失败原因是不是「临时的」。临时：断线和网络错误（`ECONNRESET`、`ETIMEDOUT`、`socket hang up`、`stream disconnected`、`fetch failed` 等）、HTTP 429/500/502/503/504、`overloaded`、限流。不算临时（照旧失败）：任务预算用完、上下文超长、401/403、未知模型、任务超时、你自己停的、写回或校验失败。
  2. runner 收尾时（`finish`）用这一轮的错误文字、`stderr` 尾巴判断，把 `transient: true` 交给 `task_finish`。
  3. `taskFinish` 新增一支：临时错误且这个任务的自动重试不到 3 次 → 回到排队，记 `retryAt`，等 1 分钟、4 分钟、15 分钟再接着做。用同一个副本、同一个 Codex 会话，给它的话和断电续做同一类：「刚才连接模型出错，这一轮中断了。先看看现在的文件和进度，已经做过的有副作用的事别重做，接着把任务做完。」不触发交接、不推送。
  4. `scheduleNow` 跳过 `retryAt` 还没到的；`taskNeedsTick` 也不为它们每 5 秒拿一次锁。
  5. 任务时限不因重试延长（`deadline` 第一次开工时定下）；重试时已经过了时限，直接按超时收尾。
  6. 重试计数在站长补充要求、任务做完时清零。每日任务同样适用。
- 网页：排队中的任务带 `retryAt` 时，卡片小字写「连接出错，稍后接着做」。
- 参考：Grok Bot `host/runner/transient-stream-error.ts`（临时/终止分类）；OpenMuse `engine/worker.ts`（丢租约回队列）；Codex `responses_retry`（退避）。
- 测试：假 codex 干到一半报 `stream disconnected` → 任务回队列、等到点后续接同一个会话并做完；报预算用完 → 直接失败；连续 3 次临时错误 → 失败并交接。等待时长用环境变量调短。

### A3 等站长回答最多挂 10 分钟

- 现状：后台模型中途问问题（`item/tool/requestUserInput`），`approvalRequest`（`vm-agent.mjs:1011`）一直等，任务算「后台在忙」，Worker 每分钟续租约，云电脑一直醒着，直到任务时限。
- 做法：等满 10 分钟（`XIN_APPROVAL_HOLD_MS` 可调）没人回：
  1. 在 `tasks` 锁里去掉 `approval`，把问题记成 `pendingQuestion`，状态回 `running`（和现有 `xin task ask` 一样，这一轮结束前仍占名额）。
  2. 回答模型：「用户 10 分钟内没有回复。问题已经记下，用户回复后会接着叫你。现在结束这一轮：最后一条消息写清楚做到哪了、要用户确认什么。」
  3. 这一轮结束后任务停在「等你确认」，进程退出、租约释放，云电脑可以睡。站长之后回答，走现有的 `task_tell`，接着同一个会话做。
  4. 站长恰好在到点那一刻回答：答案按现有逻辑进收件箱，下一轮带上，不丢。
- 参考：Agent HUD `src/crates/core/src/requests.rs`（`hold_ms: 600_000`，到点交还 agent）；OpenMuse `actions.ts`（待审提议带过期时间）。
- 测试：假 app-server 发提问、等待调到 1 秒 → 任务变「等你确认」、进程退出、不再算后台在忙；之后补充 → 续接同一会话。

### A4 任务副本放控制器自己的目录

- 现状：副本在 `os.tmpdir()/xin-task-<任务>`（`vm-runtime.mjs:36`）。正式云电脑上是 `/data/tmp`，InstaBox 会删其中 10 天没用的文件；用哪里取决于模板给的 `TMPDIR`。
- 做法：
  1. 新副本放 `~/.xin-tasks/xin-task-<任务>/`（`XIN_HOME` 的同级目录，权限 0700；测试里跟着 `XIN_HOME` 走）。不放在 `~/.xin` 里面（后台的权限配置拒绝它）也不放在 WORK 里面（会出现在「小芯的文件」里、和项目目录重叠）。
  2. 旧副本照旧能用：`prepareWorkspace` 看到记录里的路径还在就继续用；清理（`cleanupTaskTemporary`、`dropTaskFiles`）承认新旧两个根目录，各自核对归属。
  3. 任务做完时把用量数字存进任务记录，以后删副本不影响用量显示。
  4. 保留期（会删数据，**需要站长同意**，见文末）：建议做完的任务副本 7 天后在每日清理时删（结果已经写回项目，写回前的备份另存 30 天）；没做成、停了、等确认的保留到删对话为止。站长不同意就先不删。
- 回滚：退回上一版 Worker 时，旧代码清理新目录的副本会核对不过、在结果后面多一句「临时文件未能清理」，不影响任务本身。
- 测试：新任务的副本在新目录；旧路径的任务续做、删对话都正常；保留期只删「做完且超过 7 天」的。

### A5 写回失败自动还原，已写回的不算冲突

- 现状：`publishWorkspace`（`vm-runtime.mjs:174`）逐个文件替换，中途出错不回滚；进程中途被杀后重算计划，已写回的文件被当成冲突（`publicationPlan`，`:66`）。
- 做法：
  1. 冲突判断：改动的文件只有「原项目现在既不等于开工时、也不等于副本」才算冲突；删掉的文件只有「原项目里还在且不等于开工时」才算。已经等于副本的跳过不写。
  2. 写回前在备份目录写一份 `publish.json`（要改、要删、要新建的文件清单）。
  3. 写到一半抛错：按清单把已改的文件从备份拷回、新建的删掉、已删的拷回，标「已还原」，任务结果写「写回中途失败，原项目已还原」。
  4. 写到一半进程被杀：下次收尾时已写回的不算冲突、接着写完剩下的（往前补齐）。
- 参考：opencode `packages/core/src/snapshot.ts`（按内容记录、按文件还原）；Grok Bot `shared/node/atomic-write.ts`。
- 测试：第 N 个文件写入失败 → 原项目逐字节和开工前一样；预先写回一半再收尾 → 没有冲突提示、结果完整；真有别人改过的文件仍然算冲突。

### A6 读操作不再抢写锁；轮询接着上次的位置读

- `recover()`（`vm-state.mjs:72`）先用普通查询看有没有「没投影的行」，没有就直接返回，不 `BEGIN IMMEDIATE`。已用实验确认：WAL 模式下别的进程占着写锁时，打开状态库的建表语句和普通查询都不受影响，只有 `BEGIN IMMEDIATE` 会被挡。正确性：提交过但没投影的行对查询可见，崩溃后照样能补。
- `poll` 加一个可选的字节位置 `pos`：带了就从那个字节开始读到最后一个完整行，返回新的 `pos`；没带就按原来的「第几条事件」读。`history` 返回进行中那一轮时也给 `pos`。网页记住 `pos`，下次带上。新旧网页、新旧控制器任意搭配都能用。
- 参考：Agent HUD `docs/performance.md`（日志从上次读到的位置接着读，半行等下次）。
- 测试：另一个进程占着写锁时 `poll`、`sessions` 不等待；按 `pos` 读的结果和按条数读一致；半行不返回；不带 `pos` 的旧请求照常。

## B. 用量看板（PR 2）

站长选的范围：头像光环 + 点开的额度卡 + 工作台里的简版「用量」页。

### B1 数据（控制器）

- 额度：已有 `front-antigravity-quota.json`（Opus，前台每句话都会刷新）和 `antigravity-quota.json`（Gemini，跑后台任务时刷新）。每个窗口：id 以 `-5h` 结尾是 5 小时、`-weekly` 是每周；剩余比例；重置时间；读取时间。
- 消耗速率：每次读到新额度时追加一条到 `quota-history.jsonl`（留 14 天）。同一个窗口（重置时间相同）最近 2 小时内的读数算出每小时用多少；最新读数超过 30 分钟就不预测；预计用完的时间晚于重置时间也不显示。
- 读数过期：重置时间已过的窗口按「已重置」显示，不再用旧比例。
- token：`model-stats.jsonl` 每轮一条（模型、输入、缓存命中、输出）。上限从 1 MB / 3000 条提到 2 MB / 8000 条，保证够 30 天。后台整理记忆的用量不在里面（它有自己的每日上限），页面不显示这部分。
- 新 op `usage`：返回各模型额度（窗口、已用比例、重置时间、预计用完时间、读取时间）、最近 30 个北京日按模型的 token、今天/7 天/30 天合计和缓存命中率、数据最早到哪天。
- 现有轮询 `tasks` 顺带返回一个很小的 `glow`：用得最多那项额度的等级（`ok` / `warn` / `high` / `out` / 没有读数），给首页和工作台的光环用，不多发请求。

### B2 光环

- 等级照 Agent HUD：已用不到 70% 绿，70% 起黄，90% 起红，用完红色并变暗；没有读数时不上色，只留中性描边。
- 位置：首页「小芯」卡片、聊天面板标题（全屏工作台时它在中间那栏）里的小芯头像外面一圈。
- 动：平时慢呼吸；小芯在干活（有任务在做，或正在回话）时呼吸加快。系统设了减少动态时不动，只留颜色。
- 头像单独成一个按钮（首页卡片标题现在整块是按钮，按钮里不能再套按钮），点开额度卡；其余地方照旧进工作台。

### B3 额度卡

## C. 机外加密备份（第二批，站长 2026-11-12 说按建议来）

**目标**：云电脑坏了、被删、账号出问题时，小芯的记忆、对话、任务记录能找回来（研究笔记 4.4）。

**放哪**：Worker 已有的 Durable Object 类 `XinTaskSupervisor`（SQLite 型），单独一个实例 `xin-backups`，和任务租约的实例 `xin-tasks` 分开存。没有用研究笔记里写的 R2，因为 R2 有三样会话里查不到也加不了：账号开没开通 R2、部署令牌有没有 R2 权限、新的加密密钥要放进 GitHub Secrets。缺任何一样，部署都会失败。一份约 0.6 MB；Durable Object 一个值最多 8 MB，免费版一个对象 1 GB，够用。同一个类换个实例名，**不需要迁移**。

**内容**：云电脑打一个包 `~/.xin/exports/state-YYYYMMDD.tar.gz`（`backupExport`），里面有：
- 状态库 `workflow.sqlite` 的一致快照（`VACUUM INTO`）：记忆、会话索引、学习画像都在里面。
- 直接写成文件的部分：对话过程 `runs/`、消息 `messages/`、会话 `sessions/`、每日清单、统计和额度读数等。

正式机核对过：对话过程大部分是直接写成文件的，只备份状态库会丢掉大部分对话内容，所以要打包。

不放进包里的：
- 网关密钥 `*.key`、推送私钥和订阅 `push/`、回调令牌；
- 控制器脚本、锁、预览、本地导出、写回备份、终端日志——这些能重建，或者不该外传。

**时机**：北京时间 9:10、21:10 的每日任务定时调用之后（电脑醒着）。今天的备份已经有了就跳过，所以 9:10 成功了，21:10 不会再做一遍。

**流程**：
1. Worker 调云电脑上的新操作 `backup_export`：打今天的包（已经有了就复用，本地只留 3 份），返回路径、大小、sha256。
2. Worker 经 InstaBox 的 `files/content` 取原始字节，核对大小和 sha256。
3. 加密：AES-256-GCM。密钥 = HKDF-SHA256（站长登录密码，每份随机 16 字节盐，`liming-xin-backup-v1`），每份随机 12 字节 IV。不压缩：免费版每次调用的 CPU 只有 10 ms；同样的原因，密文全程按二进制传、按二进制存，不转 base64（0.6 MB 转一次就要 30 多 ms）。
4. 存成 `backup:YYYY-MM-DD`：版本、日期、时间、大小、sha256、盐、IV，加二进制密文。
5. 删 30 天前的备份，和写回备份的 30 天一致。

**密钥**：从站长密码派生，备份旁边不存密钥。改了密码以后，以前的备份要用当时的密码解：网页上不收旧密码（不多开一个能试密码的口子），下载加密原件后用 `scripts/xin-backup-decrypt.mjs` 离线解。

**取回**（都要先登录）：
- `GET /api/xin/backups`：列出所有备份（日期、大小、sha256）。
- `GET /api/xin/backup?date=YYYY-MM-DD`：解密后下载。
- `GET /api/xin/backup?date=YYYY-MM-DD&raw=1`：下载加密原件 `.backup`（第一行是参数 JSON，换行后是密文；改过密码、网页上解不开时用）。
- `POST /api/xin/backup`（本站页面发的 JSON）：现在就做今天的备份，已有就跳过。正式站每次发布后的联调用它当场走一遍：导出、取回、加密、存、列出、解密下载，核对大小和 sha256。

**恢复**：新云电脑上把下载的包解进空的 `~/.xin`（`tar xzf xin-state-YYYYMMDD.tar.gz -C ~/.xin`），网关密钥照 `MACHINE.md` 重新配；控制器脚本由 Worker 下一次调用时自动装上。包里有备份那一刻排着的启动记录，恢复后可能会把当时没做完的那一轮再跑一次。

**参考**：
- Grok Bot `box-store-sync/`：云电脑里的状态同步到云端存储，坏了能整体恢复。
- WebCrypto 的标准做法：HKDF 派生密钥 + AES-GCM，每份随机盐和 IV。

**测试**：
- Worker 侧（假 InstaBox）：
  - 取文件、核对大小和 sha256；
  - 加密存储，库里看不到明文；
  - 今天已有就跳过；
  - 30 天轮换；
  - 没登录拿不到，密码不对解不开；
  - 测试站没配密码就不做。
- 云电脑侧：
  - `backup_export` 返回的 sha256 和文件一致；
  - 包解进空目录后，记忆、对话过程、清单都在，密钥和推送私钥不在。
