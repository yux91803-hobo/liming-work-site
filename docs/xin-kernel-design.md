# 小芯内核改造设计（修正后的 B）

状态：**草案，等站长确认**。北京时间 2026-11-13。确认前不动正式代码。

依据：
- 两轮架构研究。结论和架构图在 https://claude.ai/artifact/GoopetX69gn6o1BeXKVSTj （只有站长能打开）。
- 2026-11-13 在小芯电脑上的私有端口实测，见 §9。

站长已定（2026-11-13）：不加钱，也就是不租常开的机器、不改用按量付费的模型。按修正后的 B 走：产品和数据保留，重写内核。

## 1. 要解决什么

下面这些问题是现有结构造成的，修局部 bug 解决不了：

1. **没有常驻的状态主人。** 每个请求都在云电脑里新起一个进程：InstaBox exec 往返约 0.2 秒，node 启动再加约 0.07 秒。进程之间靠 `flock` 文件锁和 SQLite 协调，另外还要一个每 5 秒转一圈的看门狗。#106–#135 里大约 5 个 PR 修的是进程、锁和生命周期问题。
2. **回复没有流式。** 网页每 0.7–1.3 秒轮询一次。
3. **小芯没有闹钟。** 提示词明写「你没有闹钟」（`vm-persona.mjs`），做不到一次性提醒。定时任务只有 Worker 里写死的两个 cron。
4. **后台结果回来后不能重新规划。** 交接只有「交付、安静、继续原任务」三种结果。
5. **状态存了两份。** SQLite 日志一份，JSON/JSONL 投影又一份。
6. **模型、执行器、工具没有稳定接口。** 前台 Gemini 用的是自己发明的「文字里夹 JSON」协议。接安卓或换执行器都得改控制器。

**不在这次范围内：** 换掉 Codex、换掉记忆库、改学习台和网站、改像素小芯、改天启的功能、引入调度引擎或 Agent 框架、加钱。

## 2. 总体结构

```
网页（电脑/平板/手机）        安卓平板·伴侣应用（以后）
   │ HTTPS + SSE 流式              │ WSS，平板主动连出
   ▼                               ▼
┌──────────── Cloudflare 常驻层（永远在线，不执行模型输出）────────────┐
│ Worker：登录、转发、流式透传                                          │
│ Durable Object：日程/提醒、待送达、推送、叫醒和租约、设备中枢、端口令牌 │
└──────────────────────────────────────────────────────────────────────┘
   │ HTTPS → InstaBox 私有端口（令牌；请求本身会叫醒电脑）
   │ ← 回调：通知、日程、忙到几点
   ▼
┌──────────── 云电脑内核（一个常驻进程，电脑会睡）────────────────────┐
│ 统一收件箱 → 大脑循环（上下文组装）                                   │
│ 任务管理（带租约）· 工具闸门（四档）· 记忆（带证据）· 状态库 SQLite    │
└──────────────────────────────────────────────────────────────────────┘
   │ 模型线路              │ 执行器                │ 工具
   ▼ Responses / ACP       ▼ app-server / ACP      ▼ 进程内 / MCP
 网关模型、Antigravity    Codex（容器内）、天启    浏览器代理、设备、日程
```

## 3. 谁负责什么

规则只有一条：**一类事情发生的那一刻，谁一定醒着，谁就是这类状态的唯一记录。**

| 状态 | 唯一记录在 | 理由 |
|---|---|---|
| 身份、登录、设备名单、端口令牌 | Cloudflare | 电脑睡着时也要能验证 |
| 日程、提醒（什么时候该做什么） | Cloudflare | 到点时电脑可能在睡，电脑上的定时器叫不醒自己 |
| 待送达的消息和通知 | Cloudflare | 要在网页、手机离线时先存着 |
| 对话、轮次事件、任务、记忆、学习画像、网站登录资料 | 内核 SQLite | 产生它们时内核一定醒着；数据量大、要和执行器同机 |
| 执行器的断点（Codex 线程、工作区） | 执行器自己 | 内核只记引用（线程号） |

- **Cloudflare 不只是传话和叫醒**，它管的是「什么时候」和「送没送到」。它不保存任务的执行状态，也从不执行模型的输出。
- **内核是自己数据库的唯一写者**，别的进程（执行器、空闲整理）不直接写它。
- **到点要做的事**：Cloudflare 叫醒电脑，把「日程到了」送进内核收件箱。内核来决定做什么。

## 4. 通信

### 4.1 网页 ↔ Worker

- 发消息：`POST /api/xin/send`，带 `clientId` 当幂等键，收到后立刻回轮次号。现有做法不变。
- 收回复：`GET /api/xin/stream?conv=…`，用 SSE 推。Worker 直接把内核的流原样透传（`new Response(upstream.body)`），流不经过 Durable Object，免得按在线时长计费。
- 断线续传：内核按对话给事件编号，存在 SQLite。网页切到后台再回来时，用 `Last-Event-ID` 从断点续上，不会丢消息。
- 心跳：内核到 Worker、Worker 到网页的流，每 15 秒发一行 SSE 注释。中间任何一层有空闲上限都不会断（§9）。
- 迁移期间保留现在的轮询，流式出问题就自动退回轮询。

### 4.2 Worker ↔ 内核

- 地址是 InstaBox 私有端口 `https://<端口>-<机器号>.instabox.tech`。内核只监听 `127.0.0.1`，实测可以访问（§9）。
- 认证有两层：
  - InstaBox 层：`Authorization: Bearer ibp_…`。不带令牌是 401，令牌错是 401 或 403，而且**不会叫醒电脑**。
  - 内核层：InstaBox 转发时会去掉 `Authorization` 头（实测），所以另加 `X-Xin-Auth`，内容是对「方法、路径、时间戳、请求体摘要」的 HMAC，5 分钟内有效。这样即使端口误设成公开，也进不来。
- 端口令牌：Worker 本来就有 InstaBox 密钥，由它调用 InstaBox 接口发布端口、轮换令牌，令牌存在 Durable Object 里。不用手工配密钥。
- 叫醒：请求本身就会叫醒电脑，但实测一次要 40.7 秒（§9）。所以发消息时不能让网页干等：
  - Worker 先把消息存进 Durable Object 的待送达，立刻回「收到了」，网页显示「小芯在醒」。
  - Durable Object 去叫醒电脑并送达，网页的流在内核醒来后接上。
  - 保留现在「打开小芯页面就提前叫醒」的做法（`chat.js` 里打开页面就调 `wake`），多数时候用户打完字电脑已经醒了。
- 叫醒时各种回应的处理：
  - `503` 加 `Retry-After`（恢复超过 45 秒）：重试。
  - `409 machine_cooldown`：先把消息存进 Durable Object 的待送达，告诉用户大约几分钟后处理，到时由闹钟重试。
  - `502`（内核没在跑）：Worker 走维护通道（§4.4）启动内核，再重试一次。
- 幂等：所有写请求都带编号，内核沿用现在 `commands` 表的「编号加摘要」去重。

### 4.3 内核 → Worker（回调）

- `POST /api/xin/kernel-event`，带 HMAC。可以发这几类：通知或推送、日程的增删、「忙到几点」（Durable Object 据此续活动租约）、任务状态摘要。
- 内核有一张发件表，没收到 2xx 就重试；Worker 按事件编号去重。

### 4.4 维护通道（exec）

继续用 InstaBox exec，但只管这几件事：
- 部署：照现在 `agentScript()` 按内容哈希上传模块。
- 启动、重启内核。
- 健康检查。
- 备份导出。

聊天不再走 exec。

## 5. 内核内部

### 5.1 进程和生命周期

- 一个 Node 22 进程，交给 systemd 用户服务管理，设 `Restart=always`。电脑上已经有用户级 systemd，见 `vm-reaper.mjs`。
- 电脑暂停再恢复时，内存和进程都在，内核接着跑。冷启动由 systemd 拉起；没拉起来就由 Worker 经维护通道启动。
- 租约、超时一律按墙上时间（`Date.now()`）判断，不信任暂停前设的定时器。电脑暂停期间时钟会跳。
- 内核内存超过阈值，并且没有任务在跑时，自己重启一次。

### 5.2 状态库

- 只用一个 SQLite（`node:sqlite`，WAL），内核是唯一写者。现有的 `documents / appends / commands / launches / handoffs` 表先原样保留，新表只加不删。
- 迁移期间 JSON/JSONL 投影照写，让旧控制器能随时接手（回滚用）。等第 5 步才停写、删除，**那一步会删文件，要先问站长**。

### 5.3 统一收件箱和大脑循环

- 收件箱一张表，五种事件：用户消息、任务完成、日程到点、设备事件、系统事件。
- 每个对话同一时间只有一轮在跑。新消息来时：
  - 模型线路支持中途补充，就补充进去（沿用现在的 steer）。
  - 不支持，就排到下一轮。
- 一轮的过程：组装上下文（人设、记忆、学习画像、跨对话回忆，沿用 `vm-context.mjs` 和 `vm-persona.mjs`）→ 调模型线路，流式输出 → 工具调用经过闸门 → 事件写进 SQLite → 推给订阅的网页。
- 后台任务完成后，它的结果作为一条收件箱事件，交给同一个大脑、用同一套工具处理：可以告诉用户、派下一步，也可以不出声。现在的「交付、安静、继续」三种结果变成了大脑能做的普通动作。`vm-handoff.mjs` 里控制上下文长度的规则保留。

### 5.4 任务管理

- 任务表的字段：编号、对话、类别、状态、执行器、执行器引用（如 Codex 线程号）、租约到期时间、尝试次数、时间。
- 状态有：排队、执行中、验收中、完成、失败、取消、中断。
- 内核里有一个循环，按并发上限（沿用现有的通道）取任务启动执行器，并定期续租约。
- 内核重启后，扫描「执行中且租约过期」的任务：执行器支持恢复就恢复（Codex `thread/resume`）；不支持就标成中断，再发一条收件箱事件，让大脑告诉用户。
- 验收和写回（网页验收、编译校验、推送）保留现有函数，作为任务里的步骤。
- 失败分类沿用 `vm-retry.mjs`。换模型重试只在还没执行命令、还没说话之前做，规则和现在一样。
- InstaBox 活动租约：内核通过回调告诉 Durable Object「忙到几点」，由 Durable Object 继续按现在的方式续租。

### 5.5 三个接口

| 接口 | 形状 | 第一批实现 |
|---|---|---|
| 模型线路 ModelRoute | `stream({model, effort, instructions, input, tools})`，流式返回文字、工具调用、用量和结束事件 | Responses（WorkBuddy 网关的 DeepSeek / GLM / Kimi）；ACP（`agy acp` 的 Gemini，先包住现在的文字协议） |
| 执行器 Executor | 照 ACP：开会话、发提示、中途补充（可选能力）、取消、恢复、事件流、请求授权（交给工具闸门） | Codex app-server（包住 `vm-runtime.mjs` 的 `appServer`）；通用 ACP；天启 Harness 保持原样 |
| 工具 Tool | 照 MCP：列出工具（名称、说明、参数格式、风险档），调用 | 进程内工具：记忆、日程、文件、派任务、回复、小芯动作；浏览器先在进程内，接口形状一样；第一个外部工具（安卓）出现时再接 MCP 客户端 |

模型回退分阶段：还没出第一个字就失败，换下一条线路；已经出了字，就不重试。

### 5.6 工具闸门（四档，借鉴 OpenBot）

| 档 | 含义 | 例子 |
|---|---|---|
| 直接做 | 不问 | 查记忆、读文件、派只读任务 |
| 本次已同意 | 用户这次请求里已经说了要做 | 「帮我把这个推上去」里的推送 |
| 先问 | 停下来问用户 | 删文件、对外发消息 |
| 交给站长 | 只能站长亲手做 | 输密码、输验证码 |

天启不经过闸门，保持站长确认过的完全放权。

### 5.7 记忆

`vm-memory.mjs` 和 `vm-memory-idle.mjs` 保留。只加一样东西：借鉴 Graphiti，加上「生效时间」和「失效时间」两个字段，记的是事情在现实中什么时候成立、什么时候不再成立，和记录时间分开。只加字段，不改已有数据。空闲整理改成内核里的低优先级任务，不再单独起进程，预算不变。

## 6. Cloudflare 常驻层

- **扩展现有的 `XinTaskSupervisor`，不新建类。** 它已经是 SQLite 型 Durable Object，所以不涉及类迁移，备份实例 `xin-backups` 也不动。新建或删除类都算 Durable Object 迁移，要先问站长。
- 新增四样职责：
  - 日程：一张表，闹钟设到最早到期的那一条。
  - 待送达：内核暂时连不上时的消息，以及要推送的通知。
  - 叫醒和重试：遵守 `Retry-After`，遇到冷却就等冷却结束。
  - 端口令牌的发布和轮换。
- 以后再加设备中枢：安卓伴侣应用用可休眠的 WebSocket 连上来，空闲时不计时长。
- 现有两个 cron（8:55 叫醒，9:10 和 21:10 每日任务）改成日程表里的三行。cron 本身留着当保险，每次只是让 Durable Object 检查一遍有没有漏掉的。
- 推送用 Web Push。先做不带内容的推送：只签一个 ES256 的 VAPID 凭证，手机收到后再带登录态拉取内容。这样 Worker 不用加密消息体，CPU 开销最小。
  - 如果用 iPhone，要先把网站「添加到主屏幕」才能收到通知。

## 7. 安全边界

| 边界 | 规则 |
|---|---|
| 公网 → Worker | 站长密码登录和签名 cookie，不变；只转发已登录的请求 |
| Worker → 内核 | 两层认证（§4.2）；内核只监听 127.0.0.1；没有令牌的请求不会叫醒电脑 |
| 内核 → 执行器 | 不变：bwrap 容器、独立网络、推理代理（一次性令牌、模型锁定）、出网代理（只允许公网 80/443）、浏览器代理 |
| 大脑 → 工具 | 四档闸门（§5.6） |
| Cloudflare → 设备 | 一次性配对码；设备密钥存在 Durable Object；内核只能经设备中枢发请求；平板本机还有自己的开关 |
| 天启 | 照旧完全放权，数据和小芯隔离 |

## 9. 实测记录（2026-11-13）

测试方法：在小芯电脑上另开一个私有端口，跑一个只回模拟数据的小服务，从开发沙盒发请求。测完删除端口、服务和文件。小芯自己的 3 个端口没有动。

注意：客户端在开发沙盒里，要经过代理，不是从 Cloudflare 发出的。所以绝对数字会有出入，相对比较是成立的。

| 项目 | 结果 |
|---|---|
| 不带令牌 / Bearer 令牌错 / `_token` 错 / 令牌对 | 401 / 401 / 403 / 200 |
| 程序能不能看到 `Authorization` 头 | 看不到，InstaBox 转发时去掉了。所以内核要有自己的认证头 |
| 服务只监听 127.0.0.1 | 能通过端口访问 |
| 自定义头和编码过的查询串（审查时补测） | `X-Xin-Auth` 原样到达程序；`%2F` 这类编码的查询串一个字节不变；只有 `Authorization` 被去掉。所以内核按收到的 `req.url` 验签可行 |
| 往返时间（中位数 / 90%） | 私有端口 GET 99 / 575 毫秒；POST 2 KB 97 / 117 毫秒；对照现在的 exec 跑 `true` 198 / 578 毫秒，现在每个操作还要再加约 70 毫秒 node 启动 |
| 流式（每 250 毫秒发一条，共 40 条） | 到达间隔 244–253 毫秒，没有攒包；第一次连接 571 毫秒收到响应头（含建立 TLS） |
| 连接上 120 秒没有任何数据 | 没断，120.6 秒时收到那一条 |
| 连接上 330 秒没有任何数据 | 从开发沙盒发，300 秒整被断开；从小芯电脑自己发到同一个地址，330 秒正常收到。所以断开的是开发沙盒的代理，不是 InstaBox。Cloudflare 那一段的空闲上限没测到，流里一律每 15 秒发一次心跳 |
| 10 分钟流，每 15 秒一次心跳 | 完整收到 40 条，间隔 15.0 秒，没断 |
| 电脑空闲暂停时，不带令牌的请求 | 401，5 秒后电脑仍是暂停状态。证实乱发的请求叫不醒电脑，不会白白消耗运行时间 |
| 从空闲暂停中叫醒（带令牌） | 能叫醒，但这一次用了 **40.7 秒**，离 InstaBox 的 45 秒上限很近。叫醒后还是原来那个进程（进程号相同，运行时长连续），之后往返约 0.1 秒，流式正常。只测了一次。现在的 exec 路径叫醒时一样要等恢复，所以这不是新路径带来的退步 |

## 10. 迁移步骤

每一步都能单独上线、单独回滚；旧路径一直留到后一步也稳定为止。每一步都走正常上线流程：`npm run check`、`npm run test:e2e` 全过，测试站冒烟，正式站联调。

| 步 | 做什么 | 回滚 |
|---|---|---|
| 1 内核外壳和新传输（行为不变） | `vm-kernel.mjs` 先只做 HTTP 入口，收到请求就在本机调用现有控制器，并把运行事件文件推成 SSE。Worker 加私有端口客户端，失败时退回 exec。网页加 SSE，失败时退回轮询。收益：每次调用少一次 InstaBox exec 往返；回复变流式；私有端口在正式环境验证 | Worker 开关 `XIN_TRANSPORT=exec` |
| 2 内核接管状态和调度 | 内核成为 SQLite 唯一写者，ops 在进程内执行；去掉 `flock`、`lockedCall`、看门狗；`runner` 改成带租约的任务管理；Codex 和 Antigravity 执行器各包一个适配器。按操作分批：先只读的（poll、tasks、usage、记忆列表），再 send/steer，再任务执行，最后每日任务和空闲整理 | 停内核。旧控制器读写同一个库，表只加不删，投影照写 |
| 3 统一收件箱和前台循环 | 收件箱；前台循环改用模型线路接口；交接改成收件箱事件；工具闸门四档 | 开关 `XIN_FRONT=legacy` 用旧 `frontTurn` |
| 4 日程、提醒、推送 | Durable Object 管日程和推送；内核加 `schedule.*` 工具；删掉提示词里「没有闹钟」那句 | 关开关；日程表保留，不删 |
| 5 收掉双份状态 | 停写 JSON 投影，删旧文件 | **会删数据，先问站长**；删之前做加密备份 |
| 6 安卓平板 | 先单独验证伴侣应用（如 mobilerun-portal 的反向 WebSocket）能不能对接 Durable Object，再做设备中枢和 `device.*` 工具 | 关开关；设备名单保留 |

第 1、2 步只改结构，不加新功能，用来控制「第二版做过头」的风险。

## 11. 测试

## 12. 风险和还没验证的事

| 风险 | 对策 |
|---|---|
| 重写做过头 | 先定接口；第 1、2 步不加功能；按操作分批搬 |
| 内核一个进程挂了，小芯就整个停了 | systemd 自动重启；Worker 发现内核不在就经维护通道拉起；状态在 SQLite 里，进程崩了也不丢 |
| 长时间运行内存越来越大 | 用量看板显示内核内存；空闲时超阈值自己重启 |
| 电脑在冷却期叫不醒 | Durable Object 先存消息，告诉用户大约几分钟后处理 |

还没验证：
1. 从 Cloudflare 发出的流式透传：在第 1 步用开关在正式环境验证，失败自动退回。

4. 安卓伴侣应用能不能对接：第 6 步之前单独验证。
5. 长时间运行的 Node 进程经过很多次暂停和恢复后是否稳定：第 1 步上线后观察。

## 14. 第 1 步的边界（站长 2026-11-13 确认设计时提出）

站长确认了修正后的 B，可以开始第 1 步。确认时提了五条边界，第 1 步按下面这样落实。原则是能复用现有机制就复用，不另起一套。

### 14.1 存好了才说收到；待送达和正式轮次一一对应

- 只有「发消息」（`send`）走待送达。存在 Durable Object 实例 `xin-inbox` 里，一条消息一行。
- 写入完成之后，Worker 才回复「收到了」。写失败就回「没存上，请再发一次」，也不会去叫醒电脑。
- 编号用网页原有的 `clientId`，不另造。同一个编号贯穿四处：
  - 待送达那一行的编号；
  - 内核去重表的 `send:<clientId>`；
  - 控制器的回执 `messages/<clientId>.json`；
  - 送到之后回来的轮次号 `run`，记在待送达那一行里。
- 同一编号再发一次：内容相同，就回原来那一行的状态，不重复送；内容不同，就是冲突，不送。
- 补充消息（`steer`）不走待送达。补充只在一轮正在跑的时候发，这时电脑是醒着的。它照旧由控制器先存好、再回成功，同样按 `clientId` 去重。

### 14.2 切回旧 exec 之前防止重复执行

内核的每个回应都带 `X-Xin-Kernel` 头。据此把一次请求分成四种结果：

| 结果 | 怎么判断 | 怎么处理 |
|---|---|---|
| 成功 | 有内核头，`ok: true` | 用结果 |
| 做了但出错 | 有内核头，`executed: true` | 原样报错，**不切回 exec** |
| 确定没执行 | 有内核头且 `executed: false`（认证没过、模块缺了、太忙）；或 InstaBox 自己的 401/403（端口令牌不对）、503（正在叫醒）、409 冷却 | 修好能修的（换令牌、装钥匙、启动内核）后重试一次，或切回 exec |
| 不知道执行没有 | 超时、连接断了、没有内核头的 502/504 | 只有可以安全重来的操作才切回 exec，其余报「不确定刚才的操作有没有做完，请刷新看看」 |

- 可以安全重来的操作有两类：
  - 只读的：`poll`、`history`、`sessions`、`tasks` 等，清单写在代码常量里。
  - 带 `clientId` 由控制器去重的：`send`、`steer`、`task_tell`、`task_stop`。
- 内核那边的请求超时、对方断开时，**不杀**已经启动的控制器进程，让它做完并存下结果。之后再来的同编号请求，拿到的就是存下的结果。
- 回滚也保持幂等。关掉开关后，待送达里的消息改走 exec，编号不变。如果整个 Worker 版本回滚到第 1 步之前，待送达里还没送出去的消息会停住，等代码回来才接着送。所以手动回滚前要先确认待送达是空的。

### 14.3 传输是流式，模型生成不一定是

- 第 1 步的 SSE 只是**传输方式**变了：控制器把事件写进运行记录，内核马上推给网页，不用再等下一次轮询。
- 前台模型现在一次返回完整答案（Antigravity 命令行），所以回复仍然整段出现。网页里「回答是整段到的，看不到一个字一个字地写」这句说明保留；不做打字机效果，也不把整段答案拆开假装在流式生成。
- 真正逐字生成要等第 3 步：先有模型线路接口，再接上支持流式的线路。

### 14.4 定时重试和送达要有持久的补偿

靠的是好几层，不靠哪一次单独的叫醒，也不靠平台默认的那几次重试：

- 每一行自己记着：状态、尝试次数、下次尝试时间、租约到期时间、等待原因（在叫醒 / 冷却到几点 / 在重试）。
- 闹钟一开始就先把自己往后再定一次（两分钟），再去干活。干到一半实例被回收，闹钟到时还会响。
- 每次尝试前先写租约。尝试中途实例没了，租约过期后由闹钟接着送。
- 退避：5 秒、15 秒、30 秒、1 分钟、2 分钟、5 分钟，之后每 10 分钟一次。InstaBox 给了 `Retry-After` 或冷却结束时间的，按它给的时间。
- 打开网页（`greet`、`wake`）和每天的定时任务，都会顺手「踢」一下待送达。有没送完的，就把闹钟提前。
- 24 小时还没送到，就标成「没送到」，网页上显示出来，**不会悄悄丢掉**。送到或失败的记录留 7 天后清理。
- 按先来后到送。前面一条因为电脑叫不醒、冷却、太忙卡住时，这一轮就不送后面的了，免得顺序乱。

### 14.5 内核自己的认证

- 钥匙是 Durable Object 随机生成的 32 字节，跟 InstaBox 端口令牌、站长密码都没有关系。Worker 用 InstaBox 文件接口把它写成电脑上的 `~/.xin/kernel-keys.json`，权限 0600。内核发现文件变了会重新读。
- 签名：用 HMAC-SHA256 签「方法、路径加查询串、时间戳、随机数、请求体的 SHA-256」，放在 `X-Xin-Auth` 头里。
- 防重放：
  - 时间戳前后 5 分钟内有效。
  - 用过的随机数存在内核自己的 SQLite（`~/.xin/kernel.sqlite`）里，10 分钟后清掉。内核重启了也认得。
- 轮换：
  - 钥匙每 30 天换一把，文件里同时留新旧两把，所以换钥匙时不断线。
  - 端口令牌也是 30 天换一次。InstaBox 回 401/403 时立刻换。
  - 内核回「不认识这把钥匙」时，Worker 重新装一遍钥匙再试。
- 日志脱敏：
  - 内核日志只记时间、方法、路由、操作名、状态码、耗时、`clientId`。不记请求头、请求体、钥匙、签名、令牌和消息内容。
  - 返回给网页的错误信息，先去掉 `ibp_`、`ibk_`、`Bearer …`、`sig=…` 这类内容。
